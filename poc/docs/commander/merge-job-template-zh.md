# 批次合并 chat 启动模板

仅在总协调接受三个完整功能（或全部功能结束时的最后余数）后实例化。准备提交、局部验收和修复子项不独立计数。合并 chat 使用 Astra / ultra、独立 managed worktree，并占一个活跃 job 槽。

启动时由总协调填入：批次编号、源 checkout、预期旧 main SHA、按依赖排序的功能编号/候选 SHA、合同和独立报告路径、原始证据位置、已批准的公共接口变更及需要携带的总协调文档提交。

## 执行任务

1. 核对实际模型、worktree、干净状态、旧 main、候选与所有依赖提交的存在性及祖先关系。Regional BFT gitlink 保持既定 pin，源 checkout 不切分支。禁止重置现有工作或改写功能分支历史。
2. Docer 核对批次接口和合同是否相容；Verifier 在合并前从合同与独立预期形成集成检查清单。清单覆盖跨组件的身份/编码、持久化、原子提交、时间和依赖变化。
3. 在 `codex/poc-integration-<批次>` 中按依赖合并已接受的候选，保留各功能历史。单一 Builder 处理集成接线与冲突；超出已批准语义的改动交总协调决定。每次解决冲突后检查实际 diff，公共 manifest/lockfile/types/proto 串行处理。
4. 将候选集成结果保存为准确 SHA。Verifier 独立复核；Tester 在该 SHA 上执行约定检查，使用全宿主 `flock /tmp/megaroation-poc-heavy.lock`，记录命令、seeds、版本、原始轨迹、摘要和限制。复核或测试后代码变化时，更新 SHA 并复验受影响部分。
5. 未通过时保留候选与诊断，main 不动。通过后检查旧 main 仍为指定值，使用带旧值比较的本地引用更新将 main 指到已验证集成 SHA；若 main 已前进，停止更新并报告，禁止 force 覆盖。若 main 已被其他 worktree 检出，不直接移动其分支引用，交总协调安排安全更新。
6. 最终回复列出旧/新 main、各候选 SHA、冲突和实际改动、独立复核结果、准确验证 SHA、检查命令与证据绝对路径、未覆盖范围。总协调复核 main 后登记 merged，并发出下一批基线。没有远端推送、PR 发布或部署任务。

合并期间若某个完整功能被重新判定不满足原 gate，将其退回相应所有者；不能通过降低完成标准达到三个功能的计数。
