## Review conclusions

The proposal matches the frozen canonical boundaries:03 object codec,07 GFR-PUBLIC-1/POS-1/LIFE-1,06 opaque messages/readers and typed Publisher states. The detailed contract correctly retains the full-attempt one-block size check while permitting actual proof/body inclusion in separate q. This is important because fragment delays within the same q cannot demonstrate public incompleteness.

The shared-completeness proposal fits the source distinction between recording and acceptance. It must return separately: valid complete evidence, public incompleteness, locally missing source/verification inputs, and known invalid input. No current-tail or historical cutoff condition belongs in Publisher's recording predicate. It must preserve exact object locations and valid proof variants; H3 may not fork a second ancestry/availability algorithm to obtain the same result.

The receipt text is consistent with frozen06 §4.1: proof at q1 can identify `publication_position`, while `complete_through_q` must cover the required bodies at q2. Neither is silently equated to earliest q_avail or to G acceptance. Keeping the first verified receipt unchanged also means later reads do not replace it merely because a different proof was downloaded first. Historical native verification must remain usable after local Close/Pause/ClockUnsafe with its public basis; those facts prohibit new signatures, not validation of old ones.

The final §3.1 native-cutover sequence also conforms to frozen07 §§3/9: accept exact H1/03 version and signature-domain compatibility, configure the expected Native profile with no fixture fallback, initialize/replay genuine inputs with native verification rather than relabeling fixture checkpoints/caches, share the checker/basis, then execute real boundary cases on the named candidate. A required03 version change remains coordinator-owned. This is migration preparation, not an executed migration.

The detailed contract's per-worker pending lifecycle batch and separate irreversible signing fence is properly left an H2/H1 policy decision. The semantic requirement is reviewable now; the actual ordering, durability and acknowledgement mechanism is not yet delivered. This unresolved safety boundary must block the corresponding implementation claim even if other H3 semantics freeze.

No mismatch requiring an immediate Docer correction was found in the reviewed preparation snapshot. The six gates above remain explicit. A fresh H3 candidate must be named and independently checked after exact interfaces arrive; component history, arithmetic examples and this review are not substitutes for that check.
