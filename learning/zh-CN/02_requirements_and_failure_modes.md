# 排序器轮换的需求与故障模式

[英文原文](../02_requirements_and_failure_modes.md)

阅读日期：2026 年 9 月 16 日。本文结合[拟议架构](../../meetup_record/rotation_overview.jpg)、本地 MegaETH 规格、Zotero 文献库、学术论文和协议社区讨论，回答[会议记录](../../meetup_record/260916.md)中有关系统需求与不当行为的问题。

**核心结论：**轮换负责决定交易顺序的一方，只解决了系统中的一部分问题。设计还必须分别保证：既定顺序得到遵守、执行结果正确、数据可用、未完成的区块得到处理、批次得以发布，以及结算持续推进。每项义务都需要明确的责任主体和故障响应方式。

涉及现有协议的陈述均链接到相应规格。下文的需求、故障分类和建议属于**针对拟议架构的设计分析**，不表示 MegaETH 已经实现了这些机制。

## 1. 首先划清职责边界

架构图将**仅负责排序的排序器**与**负责执行和发布的预确认器**分开。排序器选择一个规则允许的 L1 来源区块和交易列表，对其确定的顺序签名，而不一定执行交易。预确认器生成执行结果和批次；状态提议者提交状态断言及相应的证明材料。

这是一项架构提议。本地[排序规格](../../megaeth_specs/specs/protocol/sequencing.md)尚未将这种职责拆分定义为协议接口。在该规格中，对外可见的区块生产者是获得授权的 mini-block（微区块）签名者。此外，现有的 [mini-block 签名](../../megaeth_specs/specs/protocol/blocks.md#mini-block-header-signing)覆盖交易根、**回执根**和已使用的 gas。只对尚未执行的交易顺序签名，与对这些执行相关字段签名，作出的是不同的承诺。

因此，拟议设计需要明确区分两种声明：

1. **排序承诺：**“我授权在这条链、这个轮次、这个区块上下文和这个 L1 来源区块下，按此顺序处理这些交易字节。”
2. **执行承诺：**“在指定规则和父状态下执行上述已授权输入，会得到这些结果。”

第一种签名不能证明第二种声明。只有客户端同时检查返回结果确实绑定到上述输入，验证排序签名才能防止执行器悄悄改变输入。执行正确性仍需通过重新执行、适用的证明，或明确受信任的执行服务来保证。

同样，执行器的签名只能证明是谁作出了声明，本身并不能证明声明为真。有效性证明也只证明其电路中编码的关系。如果授权排序、来源区块选择或强制包含规则没有被纳入该关系，仅有执行有效性并不能强制执行这些规则。

## 2. 将需求称为保证之前，先写清假设

可以先采用以下威胁模型，再在选择轮换协议时进一步细化：

- 候选者、当前排序器、执行器、发布者和状态提议者可能独立失效，也可能相互串通。同一台机器承担多个角色会带来相关故障。
- 用户和搜索者可能提交相互冲突、无效或处理成本高昂的请求。正确的服务必须能够承受对抗性输入，但不应承诺处理无限流量。
- 网络可能延迟消息或发生分区。必须明确：最终取得进展是否以网络最终同步为前提，以及任何固定截止时间依赖哪些时序假设。
- Ethereum 在达到最终性之前可能发生重组。Ethereum 的审查或最终性丧失属于独立的外部依赖问题，不能按定义直接归咎为排序器违规。
- DA（数据可用性）数据检索、证明生成、监控、密钥保管和管理员可用性，都有各自的假设。
- 协议分析假设密码学原语、所建模的执行规则和裁决合约正确。实现缺陷、依赖项遭入侵和升级问题需要额外审查。

只有在角色、接口和假设已经明确之后，“所有可能的不当行为”才有具体含义。下文围绕这些接口进行系统分类，并不声称穷尽所有软件漏洞或未来的经济攻击。

## 3. 我们真正需要哪些性质

| 性质 | 在本设计中的含义 | 故障示例 |
| --- | --- | --- |
| 授权有效性 | 被接受的承诺来自对其确切轮次和区块上下文拥有授权的主体。 | 昨天的领导者已被替换，其消息却仍然被接受。 |
| 输入与执行有效性 | 满足强制输入要求和资源规则；状态转移遵循执行规格。 | 遗漏存款交易，或执行器凭空增加余额。 |
| 安全性 / 一致性 | 诚实使用方不会在同一明确的保证级别下接受不兼容的历史。 | 两个冲突的排序都被当作已不可撤销地提交。 |
| 进展活性 | 在规定的网络和可用性假设下，完整区块以及后续结算阶段持续推进。 | mini-block 一直在流式输出，却始终没有完整 EVM 区块发布。 |
| 包含活性 | 到达指定提交渠道且符合条件的请求最终会被包含，或在规定截止时间前被包含。 | 区块不断产生，但某位用户符合条件的请求被永久排除。 |
| 可用性 / 可恢复性 | 必须验证或恢复服务的参与方，能够取得所需交易数据、状态和证据。 | 下一任领导者拿到了一个根，却无法恢复对应的数据。 |
| 排序公平性 | 明确的策略约束了多个本来都有效的排序中，哪些排序可以被允许。 | 为收取贿赂而违反承诺的到达顺序规则。 |
| 可追责性 | 能够使用指定裁决者可评估的证据，将违反义务的行为归责于具体主体。 | 所有人都怀疑存在审查，却无人能证明请求已被接收，或当时适用哪个截止时间。 |

这些性质彼此不同。有效的空块可能违反包含活性。两条不同分叉上的执行都可能有效，却违反一致性。即使双签可以被客观处罚，也可能在处罚发生之前就造成损失。公平的排序不一定有利可图，也不一定高效。

**公平性目前仍是一项设计选择。** MegaETH 本地排序规格约束了存款交易、L1 属性交易与普通交易之间的相对位置，但没有约束普通交易彼此之间的顺序。夹子攻击或购买优先权可能并不理想，却未必违反现有排序规则。在处罚“不公平排序”之前，必须定义：哪些人的观察有效，哪些请求符合条件，以及如何处理相互冲突的观察。Themis 表明，公平排序在普通一致性协议之外，还会增加假设和协议机制；不能用一个未定义的全局首次到达时钟，替代其基于接收者观察的顺序标准。[Themis，论文与定义](https://eprint.iacr.org/2021/1465.pdf)

**最终性也需要清楚标注。** 以下状态应分别对待：排序签名、执行预确认、完整但仍属 unsafe 的区块、从规范链上已发布输入重建的区块、已达到最终性的输入历史，以及已被接受用于提款的状态断言。OP 派生规格明确区分了输入链的最终性与输出断言的最终确认。本地 MegaETH 区块规格同样提醒：mini-block 签名不是最终性证明。[OP 派生](https://specs.optimism.io/protocol/derivation.html#about-reorgs-post-merge)；[MegaETH 区块](../../megaeth_specs/specs/protocol/blocks.md#security-considerations)

## 4. 一套实用的执行与处置术语

将故障转化为协议规则时，可以使用以下分类：

- **拒绝（Reject）：**验证者根据经过认证的上下文和确定性检查，拒绝错误消息。
- **证明（Prove）：**可转交给其他验证方的证据足以证明某项已定义的违规行为。如果还要罚没，则必须有保证金、裁决者和完整的争议处理程序。
- **恢复（Recover）：**通过超时、替代服务提供者或交接恢复服务。恢复不要求先证明对方存在恶意。
- **度量（Measure）：**通过遥测或投诉识别服务质量问题，但不将其视为已证明的违规。
- **治理（Govern）：**干预依据有记录的治理判断，而不是完全客观的协议判定条件。

这些类别可以重叠。特别是，**适合用来更换领导者的超时，并不自动成为适合罚没的证据**。本地观察到的沉默可能来自网络分区。关于可追责活性的研究表明，归责保证依赖于通信模型；其中针对特定模型的定理，并不能为在任意网络中处罚每一次未按实际时钟规定的截止时间完成的行为提供依据。[Accountable Liveness](https://arxiv.org/abs/2504.12218)

## 5. 故障分类

下列表格属于本文的原创设计分析。“证据”一栏说明需要哪些材料，不表示现有 MegaETH 合约已经接受这些证据。对每条规则，都应保留解释该规则所需的协议版本、授权状态快照、规范链上下文引用和已签名字节。

### 5.1 排序与交易准入

| 故障 / 责任主体 | 涉及性质与有用证据 | 检测、补救与处置类别 |
| --- | --- | --- |
| 未获授权或授权已过期的领导者签署排序 | 授权；签名以及规范链上的授权 / 轮次状态。 | 在每个使用消息的边界进行检查；阻止过期轮次继续生效。**拒绝**；仅当已定义对应违规时才能**证明**。 |
| 领导者对同一个排他性位置签署不兼容的承诺 | 一致性；两个已签名载荷，以及用于认定两者属于同一位置 / 上下文的规则。 | 传播证据；停止将相关分支视为已确定；通过恢复协议选择一条规范分支。**证明 + 恢复**。 |
| 领导者签署格式错误的字节、不支持的交易类型，或结构上不可能成立的列表 | 输入有效性；已签名字节和适用的解析 / 资源规则。 | 确定性拒绝；保留证据；替换持续出错的领导者。**拒绝**，部分情况下可以**证明**。 |
| 领导者排入的交易，在按顺序执行后形成的状态下无效 | 有效性 / 进展；承诺绑定的父上下文、交易列表和执行 / 准入轨迹。 | 应用预先确定的拒绝 / 过滤规则。能否追责取决于仅负责排序的领导者作出了什么承诺。**拒绝 / 恢复**；不能自动罚没。 |
| 领导者遗漏必需的 L1 派生输入，或将其顺序排错 | 派生有效性 / 包含；规范链上的来源区块数据和提交的列表。 | 独立派生强制前缀；拒绝与之冲突的输入。如果签名义务覆盖该前缀，则可**拒绝 + 证明**。 |
| 领导者无限期排除某个普通用户 | 包含；准入回执或公开排序的队列、资格条件、可用容量和截止时间。 | 缺少这些事实时，投诉只能算观察结果。可增加强制包含路径，或以回执为依据的规则。**度量 / 恢复**；可能进一步**证明**。 |
| 领导者为了 MEV 重排交易、出售优先权，或利用私有订单流 | 公平性 / 隐私；仅靠观察到的交易顺序，通常不足以证明接收顺序策略遭到违反。 | 先决定策略；考虑可观察的准入、加密或公平排序共识。**度量 / 治理**，或在新增规则下进行**证明**。 |
| 领导者选择不被允许、过旧或不在规范链上的 L1 来源区块 | 派生有效性 / 进展；父区块的来源区块、引用的 L1 区块头、时间戳和规范链上下文。 | 通过派生检查区分规则允许的裁量空间与违规；单独处理真实的 L1 重组。**拒绝 / 恢复**。 |
| 用户用无效请求或成本高昂的失败尝试淹没准入 / 执行服务 | 容量 / 包含；负载轨迹和可复现的有效性判定行为。 | 对预处理和队列设限；使准入与执行规则一致；对昂贵操作计量。通常是**度量 + 恢复**，不属于领导者违规。 |

仅负责排序的职责边界，使第四行尤其重要。假设 Alice 当前的 nonce 为 7，并提交 nonce 分别为 7 和 8 的两笔交易。即使两个签名都是真实的，先排列 nonce 为 8 的交易，在该状态下也可能不满足准入条件。两笔单独来看余额都足够的交易，也可能在顺序执行时变得无法支付。需要决定：领导者是否保证交易满足准入条件，是否在签名前取得执行器反馈，还是仅承诺一份输入日志，再由确定性过滤规则将其映射为可执行交易。

如果允许过滤，就必须精确规定何时跳过某项输入，以及用户如何验证这一决定。否则，“执行器可以删除无效交易”就会变成一个无法追责的审查接口。如果禁止过滤，则必须避免单个不满足准入条件的条目造成规则未定义的永久停机。

**执行回滚的交易是另一回事。** 一笔已按协议准入的交易，可能执行后返回失败、消耗 gas，并产生失败回执。这不一定意味着交易无效或执行不诚实。MegaETH 特有的资源上限例外需要单独规定。“每笔交易都执行成功”不是合适的通用有效性要求。

其他 rollup 中关于准入与执行规则不一致的具体研究，说明了攻击者以低成本提交被拒绝工作所带来的风险。该研究报告了针对当时存在漏洞的实现的 denial-of-sequencing（阻断排序）攻击；这**不能**证明 MegaETH 存在对应漏洞。[Li et al., CCS 2025](https://zzzihao-li.github.io/papers/ccs25.pdf)

### 5.2 执行、预确认与扣留信息

| 故障 / 责任主体 | 涉及性质与有用证据 | 检测、补救与处置类别 |
| --- | --- | --- |
| 执行器插入、删除已授权条目，或改变其顺序 | 排序完整性；排序器承诺、完整输入，以及执行器将输出与输入绑定的认证材料。 | 按规定的排序到执行映射进行比对。证据完整时可**拒绝 + 证明**。 |
| 执行器报告错误的回执、gas、日志或状态 | 执行有效性；经过认证的声明和正确执行的证据。 | 独立执行，或使用适用的证明 / 争议系统。**拒绝 / 证明**；通过替换运营者恢复服务。 |
| 执行器向不同客户端展示不兼容的结果 | 一致性；同一上下文下相互冲突的已签名执行声明。 | 跨客户端监控；暂停受影响的保证级别；裁决已定义的冲突。**证明 + 恢复**。 |
| 领导者只公开排序根，却扣留交易字节 | 可用性 / 进展；一个已签名的根不能证明任何特定接收者已收到对应字节。 | 在承诺成立之前要求数据可检索，或要求副本持有方确认已收到数据；用检索截止时间触发恢复。**恢复**；若要**证明**违规，必须增加可用性义务。 |
| 执行器收到排序后，却扣留执行结果或预确认 | 实时活性 / 公平交换；交付确认，以及承诺的服务截止时间（如果有）。 | 替代执行器或明确的故障切换；避免因执行器沉默而归咎排序器。**度量 / 恢复**，部分情况下可以**证明**。 |
| 执行器输出部分 mini-block，却始终不完成对应的 EVM 区块 | 区块与结算进展；已签名的历史前缀和完成义务。 | 应用明确的“完成或中止”规则并保留证据。**恢复**；归责需要明确的责任与时序规则。 |
| 服务提供者提前向偏爱的搜索者披露信息 | 公平性；有其他证据印证的已签名披露记录可能有帮助，但私下交付很难被观察。 | 定义信息传播义务；从多个观察点开展监控。通常是**度量 / 治理**。 |

签署一个根、将数据交付执行器、实时发布、向 DA 分发数据、在 L1 发布，以及长期可检索，都是不同事件。应分别记录。单一的“已发布”标记会同时掩盖故障发生的位置和责任主体。

Ethereum Research 的预确认讨论区分了包含承诺与执行承诺，并强调了扣留信息以及依赖受委托预确认器的问题。这些属于设计讨论，不是关于 MegaETH 的证明。对本项目的实际启示是：如果唯一的执行器永久不可用，只轮换排序器无法恢复服务。[Strawmanning Based Preconfirmations](https://ethresear.ch/t/strawmanning-based-preconfirmations/19695)；[Preconfirmation Fair Exchange](https://ethresear.ch/t/preconfirmation-fair-exchange/21891)

### 5.3 轮换、成员资格与恢复

| 故障 / 责任主体 | 涉及性质与有用证据 | 检测、补救与处置类别 |
| --- | --- | --- |
| 网络分区后，两个控制方选出了不同的接任者 | 安全性；相互冲突的激活证书及各自的授权集合。 | 采用单一、可验证的授权规则，以及相互兼容的法定人数 / 锁定规则；不能仅凭本地超时就授权形成相互竞争的已提交历史。**拒绝 / 恢复**。 |
| 旧领导者在交接后继续工作 | 授权；消息所属轮次和激活边界。 | 所有执行器、客户端和发布者都拒绝过期授权。在明确规则下可对签名行为**证明**违规；首先应**拒绝**。 |
| 新领导者从不兼容的历史前缀开始 | 一致性；交接证书、先前承诺和父上下文。 | 将激活绑定到可恢复的检查点，并规定如何处理尚未履行的承诺。**拒绝 / 恢复**。 |
| 旧领导者扣留交接状态或确认消息 | 进展；可用检查点和失败的数据检索尝试。 | 恢复必须能够在故障领导者不配合时进行；事先复制必需数据。**恢复**，但不一定能客观归责。 |
| 反复的虚假投诉迫使领导者频繁更换 | 进展 / 可追责性；投诉、证书和频率历史。 | 认证投诉来源并限制投诉量；要求满足选定的恢复阈值；拒绝伪造证据。**拒绝 / 度量 / 恢复**。 |
| 候选者操纵成员资格、选举或退出 | 去中心化 / 激励；成员快照、随机数 / 拍卖记录和保证金状态。 | 在选定的选择机制下，分析女巫身份、关联所有权、反复尝试筛选有利结果（grinding）、贿赂和提款延迟。规则客观时可**拒绝 / 证明**。 |
| 可预测的下一任领导者遭到攻击，或所有后备节点共享同一依赖 | 进展；运营与网络证据。 | 独立基础设施、提前准备的后备节点，以及最终兜底路径。**度量 + 恢复**。 |

对于 MegaETH，交接粒度受到本地规则的约束：同一个 EVM 区块中的每个 mini-block 都必须使用同一把获得授权的密钥。在区块进行到一半时切换密钥，不是可以在不改变协议的情况下透明进行的实现调整。此外，现有 mini-block 头不包含父哈希或状态根，因此，一个孤立的已签名区块头不足以确定完整、可恢复的执行历史前缀。[排序授权](../../megaeth_specs/specs/protocol/sequencing.md#sequencer-authority)；[mini-block 结构](../../megaeth_specs/specs/protocol/blocks.md#mini-block-header)

拟议的仅负责排序的领导者可以采用独立的轮换安排，但协议必须进一步说明：排序轮次如何映射到 EVM 区块，以及如何关联执行器的签名授权。当最后一个区块尚未完成时，恢复规则必须说明如何处理已经作出承诺的交易。罚没离任领导者并不能替我们作出这个决定。

### 5.4 DA、结算与最终兜底路径

| 故障 / 责任主体 | 涉及性质与有用证据 | 检测、补救与处置类别 |
| --- | --- | --- |
| 发布者延迟发布批次，或发布不同的数据 | 发布进展 / 排序完整性；批次承诺和已接受的执行历史。 | 比较承诺；允许规则指定的替代发布者接管；保持派生规则。**拒绝 / 恢复**，部分情况下可以**证明**。 |
| DA 证书无效，或数据无法检索 | 派生 / 可用性；证书验证结果和检索协议证据。 | 区分密码学上无效的证书与数据检索不可用；定义兜底 / 超时语义。**拒绝 / 恢复**；仅靠证书并不能裁决所有可用性争议。 |
| 状态提议者发布虚假断言 | 状态有效性；断言以及执行证明 / 争议证据。 | 应用实际采用的错误证明 / 有效性证明机制。**拒绝 / 证明**。仅轮换排序器不足以解决问题。 |
| 提议者、证明者或挑战者停止工作 | 结算 / 提款进展；缺失的必需动作和截止时间状态。 | 提供替换权限、监控激励，以及有资金支持的证明 / 争议运行机制。**恢复**。 |
| 攻击者在 L1 上延迟或审查挑战交易 | 结算安全性 / 进展；L1 历史、剩余争议时间和交易交付证据。 | 按假设的审查模型设置争议程序和预算。**恢复**能力可能受 L1 限制。 |
| 整个候选者集合或共享执行服务失效 | 包含 / 退出活性；快速路径完全不可用。 | 提供规定明确的 L1 提交路径、替代执行，或逃生机制，并配备所需数据和资金。取决于设计，属于**恢复 / 治理**。 |

强制包含路径和逃生通道解决的是不同问题：前者提供另一条让合格交易得到处理的路径；后者使用户在正常运行失败时能够恢复资产或状态。两者是否有用，取决于派生、数据、证明和提款方面的依赖。OP 规格描述了通过存款派生实现包含的机制；在核实 MegaETH 的实际配置与差异之前，不能直接把它照搬成 MegaETH 的延迟保证。[OP 协议概述](https://specs.optimism.io/protocol/overview.html)；[Ideal Properties of Rollup Escape Hatches](https://dicg-workshop.github.io/2022/papers/gorzny.pdf)

本地的 [DA](../../megaeth_specs/specs/rollup/data-availability.md)、[派生](../../megaeth_specs/specs/rollup/derivation.md)、[批次提交](../../megaeth_specs/specs/rollup/batch-submission.md)和[错误证明](../../megaeth_specs/specs/rollup/fault-proofs.md)页面仍是占位页面。它们指出了需要核实的主题，但没有给出完整的故障处理语义。特别是，仅仅提到 ZK fault proofs，并不足以推断每次状态更新都必须先提交有效性证明。

## 6. 文献对设计有哪些启示

在设计奖励之前，有三点值得重视：

**可追责性是需要单独设计的协议能力。** CFT-Forensics 研究如何为原本只容忍崩溃故障的协议提供密码学归责。它对本项目的方法论启示是：应保留可解释的签名证据，而不能假设运营日志已经足够。这并不会让普通的 Raft 式故障切换自动变成能够容忍拜占庭行为的安全共识。[CFT-Forensics](https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.AFT.2024.3)

**即使表面上一切正常，也必须有人检查。** Proof of Diligence 研究监控 rollup 断言的激励。这意味着本项目应当为检测、证据留存和挑战提交单独安排预算，与排序奖励分开。Economic Censorship Games 研究了有人付费实施 L1 审查时，挑战能否完成的问题，说明“存在一个诚实挑战者”并不是完整的运行假设。[Proof of Diligence](https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.AFT.2024.5)；[Economic Censorship Games](https://arxiv.org/abs/2502.20334)

**治理规则与客观罚没是不同的执行机制。** Optimism 的 Law of Chains 描述了针对被禁止的排序器行为的治理干预。它可以作为需要裁量判断的服务义务的参考，但不是证明排序器及时收到某笔交易的密码学证据。需要明确哪些保证由协议强制执行，哪些保证依赖这种判断。[Law of Chains v0.1](https://gov.optimism.io/t/final-law-of-chains-v0-1/6514/1)

## 8. 激励设计之前需要作出的决定

对于每项承诺的性质，都应能够补全下面这句话：**“主体 A 必须针对符合条件的输入 C，按条件 D 的要求执行动作 B；观察者 E 使用证据 F 检测故障；有权裁决的主体 G 采取响应 H。”**

下一次设计讨论应明确：排序器是否保证输入可执行；执行预确认究竟承诺什么；排序承诺如何绑定到 EVM 区块；交接失败后保留哪一段历史前缀；执行器和发布者如何替换；哪条提交路径能够提供可强制执行的包含保证；以及哪些违规存在客观证据。奖励和罚没公式应在这些问题有了答案之后再设计，因为不同职责会带来不同成本、偏离规则的机会，以及可归责范围的限制。
