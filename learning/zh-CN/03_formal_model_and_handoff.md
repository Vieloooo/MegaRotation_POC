# MegaETH 排序器轮换的形式化模型

[English original / 英文原版](../03_formal_model_and_handoff.md)

建议先阅读[完整流程](01_megaeth_pipeline.md)和[需求与故障分析](02_requirements_and_failure_modes.md)。
本文回答两个问题：如何形式化排序器的行为，以及轮换协议必须明确哪些决策。
下文的消息格式和要求是**拟议的研究接口**，不是 MegaETH 已有的格式，也不是一套已经完成的共识协议。
它们是设计和检验[架构草图](../../meetup_record/rotation_overview.jpg)的起点。

## 1. 先明确目标，再选择选举算法

拟议系统让一组可以轮换的运营者负责选择交易并确定顺序，由独立的执行服务生成执行结果。
它的核心目标应当是：

> 在保持已达成一致的交易历史和正确执行的前提下，替换故障或恶意的排序运营者；并在明确的网络与基础设施假设下，将服务中断控制在规定的目标范围内。

这包含几项不同的任务：选择运营者、就其权限达成一致、承诺交易顺序、执行交易、确保相关数据可恢复，以及替换发生故障的组件。
轮询安排（round-robin）只解决选择问题。
签名能够确定承诺由谁作出，却不能让该承诺自动具备唯一性、可执行性、数据可用性或最终性。

可以考察两种自然的设计方向：

| 设计 | 轮换协议决定什么 | 带来的影响 |
| --- | --- | --- |
| 轮换排序角色，保留执行服务 | 下一个排序密钥，以及它继承的交易历史前缀 | 降低候选者的执行要求，但执行器故障和审查需要单独的恢复路径 |
| 轮换完整的区块生产角色 | 排序、执行、流式传播及对应的签名权限 | 更接近当前协议对外呈现的角色，但每个接任者都需要执行能力和可用状态 |

草图采用第一种方向。
可以将它作为主要研究方案，以第二种作为比较基线。
[当前排序规格](../../megaeth_specs/specs/protocol/sequencing.md#block-production-mechanics)把排序器视为一个对外可见的整体角色，尚未定义草图中拟议的排序与执行接口。

## 2. 区分不同的时间尺度和标识符

建议在整个设计中统一使用以下记号。

| 符号 | 含义 | 为什么需要单独区分 |
| --- | --- | --- |
| `c` | 链标识与协议版本域 | 防止同一签名被解释成另一条链或另一协议下的消息 |
| `r` | 轮换任期：候选者或委员会配置固定的一段时期 | 成员组成或预定职责分配变化时更新 |
| `v` | 视图：同一任期内的一次故障切换尝试 | 成员不变、但领导者被替换时更新 |
| `b` | EVM 区块号 | 当前 MegaETH 按这一粒度确定签名权限 |
| `j` | 区块 `b` 内的 mini-block 索引 | 标识该 EVM 区块中的一段内容 |
| `k` | 拟议有序日志中的位置 | 将不同领导者任内的决策连接起来 |
| `ell = (L1 number, L1 hash)` | L1 来源区块（L1 origin） | 确定相关的 L1 上下文；它不是轮换任期 |
| `a` | 授权配置标识 | 将决策绑定到特定成员组成和密钥安排 |

在 OP 的术语中，排序纪元（sequencing epoch）与一个 L1 来源区块关联。
这里将 `r` 称为“轮换任期”，避免把两个无关的“epoch”概念混入同一条规则。
OP Stack 基线对来源区块的推进、哈希和时间戳都有约束；来源区块并不是领导者可以为了自身利益任意挑选的参数。
由于 MegaETH 的[派生规格](../../megaeth_specs/specs/rollup/derivation.md)还是占位页，其具体扩展仍需结合实现与规格确认。
可参考 [OP 派生中的批次有效性规则](https://specs.optimism.io/protocol/derivation.html#batch-queue)。

第一个原型可以在每个任期内固定委员会，并将计划内交接安排在已经完成的 EVM 区块边界。
这能减少需要同时解决的问题，但没有解决区块尚未完成时的紧急替换。

## 3. 分别建模各项权限

一个运营者可以运行多项服务，但模型仍应区分这些服务的权限。

| 权限 | 授权对象 | 轮换时需要回答的问题 |
| --- | --- | --- |
| 排序密钥 | 拟议的带签名交易顺序 | 在 `(r,v)` 中由哪个候选者担任领导者？ |
| 委员会投票密钥（若采用委员会） | 共识投票或交接证书 | 适用哪组成员和投票权重？ |
| 执行／mini-block 签名密钥 | 与执行有关的 mini-block 和数据流承诺 | 排序密钥变化时，它是否保持不变？ |
| Mega 系统交易密钥 | 具有特权的维护交易 | 是否独立管理，能否独立恢复？ |
| 批次提交权限 | 派生过程认可的数据或证书提交 | 接任者是否确实能够发布？ |
| 状态提议／证明权限 | 结算声明，以及对声明的辩护或挑战 | 其他角色故障后，结算能否继续？ |
| 配置／更新权限 | 成员、规则和紧急变更 | L2 停止出块时，它还能否发挥作用？ |

这些行是为了分析而作的职责拆分，不表示 MegaETH 当前存在七家独立运营机构或七把独立密钥。
尤其要注意，当前的[状态同步认证](../../megaeth_specs/specs/protocol/state-sync.md#payload-authentication)和 [mini-block 签名](../../megaeth_specs/specs/protocol/blocks.md#mini-block-header-signing)使用的是获得授权的排序器密钥。
如果将这一权限交给独立执行器，同时引入另一把排序密钥，就需要明确设计二者如何兼容。

现有规格已经规定了一项独立关系：[Mega 系统交易的签名者](../../megaeth_specs/specs/protocol/transactions.md#mega-system-transaction-signer-authority)与 mini-block 签名者分别跟踪。
轮换排序权时，不应无意中把这项特权一并轮换。

## 4. 定义排序签名究竟承诺什么

### 一种候选的排序消息

用于研究的消息可以包含以下逻辑字段：

```text
Order = (
    chain_and_version, authority_config, rotation_term, view,
    log_position, target_evm_block, parent_evm_block_hash,
    previous_order_digest, l1_origin_number, l1_origin_hash,
    execution_context_digest, mandatory_input_digest,
    ordered_transaction_root, transaction_count,
    block_boundary_marker, promise_conditions
)
OrderSignature = Sign(ordering_key, DomainSeparatedHash(Order))
```

交易根需要承诺**包含顺序且绑定长度的交易列表**，而不是一个无序集合。
列表对应的字节必须能够取回；只有根哈希无法执行交易。
具体编码、哈希方案、包含性证明和域分隔符仍是需要作出的设计选择。
这段伪代码不能直接当作网络消息格式使用。

各组字段分别消除不同的歧义：

- 授权与域字段确定谁有权签名，以及承诺受哪些规则约束。
- 父区块和前一排序消息字段，防止同一列表被接到另一段历史上。
- L1 来源区块与执行上下文固定那些会影响交易有效性和执行结果的输入。
- 必须包含的输入承诺，将排序消息绑定到由 L1 派生的必要前缀。
- 区块边界标记确定当前数据片段是在延续还是结束一个 EVM 区块。
- 承诺条件说明期限、保证级别，以及允许撤销承诺或应对 L1 重组的条件。

执行上下文需要有统一定义，覆盖所有与执行有关的输入，不能只挑选容易处理的字段。
例如，在作出精确的执行承诺后，时间戳、适用协议规则、费用参数和系统交易的位置都不能再由相关参与者任意决定。
本地规格中的[区块上下文](../../megaeth_specs/specs/protocol/state-sync.md#block-context)提供了有用的字段清单，但它并不是现成的排序约定格式。

排序消息可以只承诺普通交易，前提是协议同时以确定性规则规定必须包含的交易如何插入。
否则，“执行器不能修改列表”就存在歧义：插入一个必须包含的存款交易，也可能被误认为违规。
当前的[交易接纳规则](../../megaeth_specs/specs/protocol/sequencing.md#transaction-admission-and-ordering)要求在第一个 mini-block 中，将所提供的存款交易和 L1 属性交易放在普通交易之前。

### 执行响应是另一种承诺

为了便于讨论，可以写成：

```text
ExecutionAck = (
    order_digest, parent_execution_commitment,
    accepted_transaction_root, receipt_commitment,
    resulting_state_commitment, execution_status
)
```

执行确认需要独立明确其可认证的来源和语义。
其中，执行后状态字段是一项拟议的承诺：它可以在 EVM 区块完成后得到，也可以由额外设计提供。
它**不是**当前 mini-block 头中已有的字段。
当前 [mini-block 头](../../megaeth_specs/specs/protocol/blocks.md#mini-block-header)包含交易根、回执根和 gas 使用量，但没有状态根或前驱哈希。

执行器的签名可以确定它声称了什么，却不能证明执行正确。
正确性仍需通过独立验证，或者与已达成一致的输入绑定的证明来建立。
现有[状态同步信任模型](../../megaeth_specs/specs/protocol/state-sync.md#trust-model)已经明确体现了这一区分。

## 5. 承诺精确执行之前，先解决无效交易的处理方式

不执行交易的排序服务，无法完整掌握依赖当前状态的有效性信息。
例如，同一账户签署了两笔 nonce 相同的交易。
接纳时，分别看这两笔交易可能都合理，但它们不能同时作为有效的普通交易出现在同一执行序列中。
类似地，较早执行的交易可能花掉后一笔交易所需的资金。

需要明确选择以下哪一种接口：

| 接口 | 签名列表的含义 | 如何处理无效候选交易 |
| --- | --- | --- |
| 精确的可执行交易序列 | 列出的每笔交易都属于承诺执行的序列 | 在作出强承诺前取得验证确认；验证失败时有明确的拒绝和恢复规则 |
| 已排序的候选交易列表 | 列表是某个确定性接纳／过滤函数的输入 | 明确该函数，保留获接纳交易之间的顺序，并使每次拒绝都可以复现 |

第二种方案降低了排序运营者的负担，但也改变了“包含这笔交易”的含义。
协议还需要就“已排序候选列表如何映射成规范的实际执行交易列表”达成一致，并明确结算如何验证这一映射。
执行器私下采用“遇到麻烦就跳过”的策略并不够。

在精确排序的原型中，应当区分排序器的初步提议和有执行依据的承诺。
带签名的拒绝消息应指出被拒绝的候选交易、相关前序状态及拒绝条件。
一些拒绝声明需要重放执行或提供证明才能裁定；一段原因字符串不是证据。
如果执行器只是拒绝回复，反复替换排序领导者也无法修复服务。

还要区分**无效交易**与**交易本身有效、但合约调用回滚的交易**。
回滚可能正是正确的执行结果，并且仍然消耗 gas。
仅承诺包含交易，并不等于承诺兑换、铸造或转账一定成功。
关于 [BFT 与提议者承诺型预确认的研究讨论](https://ethresear.ch/t/analyzing-bft-proposer-promised-preconfirmations/17963)，有助于区分“承诺哪项性质”和“靠什么机制落实该性质”。

## 6. 基于参与者实际掌握的信息，形式化其行为

令 `h_i(t)` 表示参与者 `i` 截至时刻 `t` 的局部历史。
其中包含它实际收到的消息、自己的 L1 视图、本地状态或交易池、观察到的证书、本地计时器，以及自身过去采取的动作。
其中不包含一个全知的全局交易池、其他节点收到消息的时间，也不包含从未送达给它的交易。

行为策略是一项依赖历史的策略：

```text
pi_i(h_i(t)) -> a distribution over feasible next actions
```

即：根据局部历史，给出下一步可行动作上的概率分布。
是否随机化可以自行选择。
动作是否可行受到信息、密码学和可用资源的约束；协议规定的诚实策略则进一步限制，哪些可行动作符合协议。
排序运营者的动作集合包括：提出交易列表和上下文、签名、向选定接收者发布字节、转发证据、确认交接、保持沉默，或生成相互冲突的消息。
在理性参与者模型中，还应包含接受额外私下付款、选择基础设施投入、扣留部分交易，以及决定加入或退出。
在拜占庭模型中，则允许其在密码学和腐化假设范围内采取任意行为。

应分别定义执行器、投票者、批次提交者、状态提议者和挑战者的策略。
诚实执行器检查适用的排序与执行规则；诚实投票者检查它的投票实际上证明的那个条件。
如果投票者不执行交易，就不能把排序证书称为执行有效性证书。

区分以下三个谓词：

```text
OrderWellFormed(O, history)
Executable(O, predecessor_state, canonical_context)
PublicationComplete(O, retrieval_and_settlement_evidence)
```

第一个谓词可以涵盖身份认证、权限、列表编码、父级链接和上下文是否允许。
第二个涵盖依赖状态的有效性与执行约束。
第三个取决于明确选定的 DA 与发布规则。
如果没有机制建立这些谓词之间的蕴含关系，就不能假定一个成立会使另一个自动成立。

应分别记录排序、执行、数据可用性、L1 派生和结算的进度。
它们可以在不同时间推进；例如，数据可能先被分发到 DA 网络，之后才有人提交状态声明。
只用一个名为 `confirmed` 的变量，会掩盖这些区别。

## 7. 将交接定义为权限与历史前缀的移交

### 计划内交接

交接记录应明确旧、新授权配置、生效边界、保留前缀的摘要、支持保留该前缀的证据，以及从何处取得对应数据。
它还应明确执行检查点和尚未完成的发布义务。
同时列出尚未履行的签名承诺，以及已经确认收到、但仍待处理的请求，说明其期限与交接后的责任方。
未被移交的请求需要明确的过期或重试语义；领导者变化不应悄悄取消已经具有约束力的包含承诺。

例如：“候选者 B 在 EVM 区块 100 完成后成为排序者；继承的历史前缀结束于排序摘要 `q`；截至区块 98 的批次已经记录，区块 99–100 仍需发布。”
接任者需要足够的经过认证的数据，才能区分哪些工作已经完成、哪些尚未完成。
只有相关接口定义了去重和统一解释方式，重复发布才可能是无害的。

接收方接受新领导者，应当是因为它按照协议的授权规则验证了交接，而不是因为某个新端点自称领导者。
旧领导者可能永远继续发送消息；**权限隔离（fencing）**指的是拒绝超出其授权范围的消息。
删除旧机器上的密钥并不是协议安全性的依据。

### 紧急交接

本地超时只能说明：某个节点在选定的时间段内没有观察到进展。
它不能证明领导者恶意，也不能证明其他节点都已经超时，更不能证明此前没有产生任何承诺。
因此，替换机制需要一项经过一致认可的交接决定，以及安全的历史前缀选择规则。

[HotStuff](https://arxiv.org/html/1803.05069v6)是研究部分同步条件下领导者替换的重要原始文献。
它的安全性依赖投票、锁定和提交规则；领导者切换时需要携带先前证书的信息。
在其固定的 `3f+1` 副本模型中，证书需要 `2f+1` 票。
这个门槛本身不是完整的共识算法：只借用票数，就会漏掉防止不同视图产生冲突决定的规则。

对本项目，应选择一套已有共识协议，并明确应用究竟向它提交什么。
如果共识只对领导者分配作出提交（commit），它不会自动提交这些领导者签署的全部交易顺序。
如果共识也提交排序历史前缀，就要说明用户何时可以依赖这种更强的保证，以及额外延迟如何体现到服务中。
这里的“共识提交”指按照共识规则确定某项决定，与仅仅发送消息或提交提议不同。

后续视图可以按照所选协议的规则替换尚未提交的提议。
但不能仅仅因为更多节点现在偏好另一条历史，就抹去已经提交的前缀。
委员会成员变化也需要从旧成员配置出发验证交接；任意新委员会出具的证书不能自行赋予该委员会权限。

## 8. 未完成的 EVM 区块，是必须先解决的设计问题

假设运营者 A 为 EVM 区块 101 签署了 mini-block 0 和 1，之后失联。
按照当前[授权规则](../../megaeth_specs/specs/protocol/sequencing.md#sequencer-authority)，同一 EVM 区块中的所有 mini-block 都使用同一把获授权密钥。
运营者 B 不能简单地换一把密钥签署 mini-block 2，然后声称仍然符合这条规则。
它也不能在尚未确定有效父区块 101 的情况下，直接跳到区块 102。

可以考虑几种设计方向，但各自的影响不同：

1. **只轮换排序角色，同时维持执行器及其签名权限可用。**
   执行器可以从已经达成一致的前缀继续完成区块，但拟议排序协议仍需规定，是否允许在同一区块中更换排序者，或如何提前结束区块。
   执行器本身故障仍是另一个问题。
2. **恢复现有的获授权签名服务。**
   这可能符合运维层面的高可用方案，但其信任与密钥保管假设，不同于用另一把独立密钥替换一家独立运营者。
3. **为被中断的区块定义协议升级。**
   可能的方向包括限定适用范围的替代签名权限，或放弃尚未确定的后缀，从已完成的检查点重新构建。
   无论哪一种，都需要调整接纳、签名、派生和承诺语义；被丢弃的后缀不能曾被宣传为不可撤销。

初始模型可以把计划内轮换放在完整区块边界，并将未完成区块的恢复定义为独立转换。
只有设计好这一转换，才能声称具备完整的容错能力。
不能把这个问题藏在一句“下一个排序器接管”里。

## 9. 将期望保证变成精确义务

以下是建议证明或测试的性质，而不是已经针对草图成立的定理。

| 性质 | 拟议表述 | 必须说明的限定条件 |
| --- | --- | --- |
| 授权一致性 | 使用同一份已最终确定的授权历史的诚实参与者，对每类消息由谁有权产生达成一致 | 明确配置的最终性，以及 L1 重组时的处理方式 |
| 前缀安全性 | 诚实参与者在选定提交级别接受的历史彼此前缀兼容 | 定义这个提交级别；单个领导者签名并不足够 |
| 执行正确性 | 每个被接受的执行结果都符合已约定的有序输入和规范上下文 | 说明谁在何时检查；若允许过滤，过滤规则也是其中一部分 |
| 顺序保持 | 执行器不能悄悄插入、删除或重排精确排序承诺覆盖的普通交易 | 明确必须包含的输入，以及无效候选交易的处理语义 |
| 恢复所需数据可用 | 正确的接任方能取回足够的数据和状态，从保留的前缀恢复服务 | 明确保留时长、存储角色，以及 DA／网络假设 |
| 服务活性 | 在假定故障范围内出现故障后，协议最终仍能产生下一个有效区块 | 排序、执行、数据和权限更新路径都需要能够响应 |
| 包含活性 | 符合资格的交易在规定期限内被包含，或得到规则允许且可验证的拒绝 | 明确收到请求的证据、资格、容量分配、期限和备用路径 |
| 结算持续推进 | 已产生的历史能够继续经过发布、提议和最终裁定 | 依赖 DA、L1 收录，以及相关证明／挑战服务 |
| 可追责性 | 对于明确定义的违规，存在可以归责的证据和可用的裁定路径 | 证据可得性、挑战成本和抵押退出延迟都会影响结果 |

在前缀安全性中，“前缀兼容”指一份被接受的历史是另一份的延伸；诚实节点可以处在不同高度。
在包含活性中，符合资格不能仅仅指“用户把交易发到了某处”。
它必须涵盖承诺的接纳规则下的有效性、可验证的送达事件、可用容量或明确的队列，以及防止低优先级请求无限等待的安排。

声称故障切换存在时间上界时，应明确采用部分同步假设：在某个未知的稳定时刻之后，相关通信延迟有界，且足够多的必要参与者能够响应。
在此之前，即使服务暂停，也要保持安全性。
[HotStuff 的模型](https://arxiv.org/html/1803.05069v6#S3)提供了一种精确参照；Ethereum 与 EigenDA 等依赖需要各自的假设，不能直接套用委员会内部网络的延迟上界。

## 10. 将协议模型连接到后续激励模型

先决定哪些偏离不被协议接受，哪些属于可证明的违规，哪些仍是规则允许的选择。
然后再定义效用。
一种可能的收支分解是：

```text
utility = ordering revenue + service rewards + MEV + side payments
          - operating costs - publication/proof costs
          - penalties - lost future business
```

即：效用等于排序收入、服务奖励、MEV 和额外私下付款之和，减去运营成本、发布与证明成本、罚款，以及损失的未来业务收益。
这是一项拟议模型，不是 MegaETH 已有的支付机制。
成本与收入应归于实际承担或获得它们的参与者。
如果排序者立即收款，而执行器承担全部 DA 费用，其激励可能与集成式运营者完全不同。

对于某项具体偏离，应比较其增量收益与预期可落实的损失。
是否被检测到、能否成功裁定，以及是否有真正可罚没的抵押，都会影响这项损失。
“收益小于预期损失”只是对某种偏离的局部威慑检查，不是均衡证明；它也不能充分说明串谋、系统外破坏收益或无上界的跨链风险敞口。
[相关系统与激励笔记](04_related_systems_and_incentives.md)进一步比较这些机制。

## 11. 下一步可以形成的具体研究成果

从固定成员、明确的拜占庭故障模型、一个活跃排序者，以及显式建模的执行服务开始。
第一次安全性分析可以暂不纳入成员选择和奖励拍卖。
选择共识协议，明确其决策覆盖授权、排序历史前缀，还是二者兼有，并规定每项决定需要哪些恢复数据。

优化吞吐量之前，先用以下对抗场景检验拟议规则：

| 场景 | 设计应能回答的问题 |
| --- | --- |
| 领导者向两个客户端发送不同顺序 | 哪个承诺具有约束力，保留什么证据，两个客户端能否都声称已经获得最终性？ |
| 领导者只签署一个根，却扣留全部字节 | 此时能否达成任何共识提交，由谁提供恢复数据？ |
| 领导者产生两个 mini-block 后失联 | 按照签名规则，谁有权完成同一个 EVM 区块？ |
| 用户在轮换前刚收到包含承诺 | 谁继承该请求、期限，以及遗漏它的责任？ |
| 旧领导者被替换后重新上线 | 拒绝它的哪些消息，同时如何保留仍然有效的历史数据？ |
| 执行器丢弃一笔已排序交易 | 拒绝是否有依据，由什么确定规范的实际执行列表？ |
| 执行器拒绝所有有效排序提议 | 应替换哪个组件，如何避免不断轮换没有过错的排序者？ |
| L1 来源区块发生重组 | 哪些暂定承诺被取消，哪段前缀需要重新计算？ |
| DA 或唯一的批次提交者故障 | 能否在不违反此前承诺的情况下恢复发布？ |
| 两个网络分区选出不同接任者 | 为什么它们不能分别提交相互冲突的历史？ |
| 交接尚未完成时委员会变更 | 哪一份成员配置有权认证这次交接？ |

一个有用的首份成果是小型可执行状态机模型及上述场景，随后再为选定协议及新增应用规则给出安全性论证。
关键指标不能只有领导者切换时间：还应分别测量多久能得到下一个可执行交易顺序、完整 EVM 区块、可恢复数据，以及 L1 发布结果。
这些测量能揭示拟议拆分的哪一部分确实改善了可用性，哪一部分仍然受制于其他依赖。
