## 最影响设计的几项区分

**草图涉及协议变化，而不只是排班变化。**
已有的 [mini-block 签名](../../megaeth_specs/specs/protocol/blocks.md#mini-block-header-signing)覆盖交易承诺、回执承诺和 gas 使用量。
如果新增一种在执行前签发的签名，就需要定义它的含义，并建立执行器结果与该签名承诺之间可验证的关系。

**轮换需要继承历史前缀。**
知道谁接任，并不能确定此前签署的哪些交易必须在交接后保留。
接任者需要对应字节、经过认证的执行进度，以及分配给自己的发布义务。
如果执行服务也更换运营者，新的执行器还需要可用执行状态，或者重建该状态的方法。
第 03 篇中的转换模型是组织这些义务的候选方案，不表示这些机制已经实现。

**未完成的 EVM 区块需要单独分析。**
当前[授权规则](../../megaeth_specs/specs/protocol/sequencing.md#sequencer-authority)要求同一 EVM 区块内的签名密钥保持一致。
一条只允许在区块边界更换密钥的规则，不能直接授权在区块中途替换失联的签名者。

**身份认证、正确性、可用性和最终性回答不同的问题。**
[状态同步信任模型](../../megaeth_specs/specs/protocol/state-sync.md#trust-model)明确区分了经过认证的排序器输出和经过独立验证的执行结果。
这组笔记在讨论预确认、DA 和结算时，始终保留这一区分。

## 如何理解证据与推断

| 证据类型 | 应如何理解 |
| --- | --- |
| 本地规范性文字 | 说明当前检出的规格规定了什么；本身不能证明每个部署都与之相符 |
| 官方公开文档 | 第一方描述；具体部署参数和配置仍需验证 |
| OP Stack 基线 | 为继承的架构或比较对象提供具体参照；需要考虑 MegaETH 的修改 |
| 学术论文 | 在论文自身假设下成立的结果或构造；不会自动为拟议集成提供保证 |
| 研究／治理论坛 | 具有明确来源的提议或讨论，不是功能已经上线的证明 |
| 拟议模型或推断 | 我们对可能设计的分析，明确区别于 MegaETH 当前行为 |

MegaETH 本地的 [rollup 规格部分](../../megaeth_specs/specs/rollup/overview.md)仍在建设，因此参考 OP Stack 很有帮助。
但在未检查 MegaETH 差异的情况下，不能直接照搬 OP 的具体常数、合约布局、权限或时间保证。
mini-block 按照 MegaETH 自己的规格解释，不应将其视为标准 OP Stack 区块类型。

这次资料梳理尚未确认实际部署的注册表治理方式、精确的 DA 故障处理、批次提交前的验证关口、全部证明系统参数，或完整的中断区块恢复算法。
这些不确定之处本身就是研究议程的一部分，不能用未声明的假设填补。

## 下一步需要明确的决策

下一次设计讨论可以集中解决以下问题：

1. **轮换什么？**只轮换排序，还是同时轮换执行服务及其签名权限？
2. **早期承诺意味着什么？**确认收到请求、保证包含、确定精确顺序、保证执行成功，还是保证特定结果？
3. **由谁对哪些内容作出共识提交（commit）？**领导者分配、交易历史前缀、执行结果，还是在不同时间分别提交其中几项？
4. **崩溃后保留什么？**哪段前缀继续有效，数据存在哪里，谁能完成被中断的 EVM 区块？
5. **仅负责排序的服务如何处理无效输入？**先验证再作出约束性承诺，还是定义从候选列表到实际执行列表的确定性映射？
6. **L2 停止后如何授权恢复？**如果权限交接本身还要求已经停滞的领导者再出一个区块，它可能无法作为紧急恢复路径。
7. **哪些故障触发替换，哪些可以处罚？**超时可能足以支持恢复操作，但并不能因此证明恶意行为。
8. **各阶段的性能目标是什么？**分别衡量排序被接受、执行响应、故障恢复、发布和结算的时间。

明确这些选择之后，形式化模型才能发展为具有具体安全性和活性主张的协议方案；激励模型也才能针对可以落实的职责展开，而不是围绕一个尚未定义的“诚实排序”概念讨论。
