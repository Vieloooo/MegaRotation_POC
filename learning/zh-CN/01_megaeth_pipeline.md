# MegaETH 的完整流程：现有协议，以及排序器轮换会改变什么

[English original / 英文原文](../01_megaeth_pipeline.md)

本文回答[9 月 16 日会议记录](../../meetup_record/260916.md)中的第一组问题：排序器与状态提议者分别做什么，完整流程如何运作，以及拟议的轮换系统会介入哪些环节。
最关键的区别是：现有协议对外提供的是**一个产生带有执行结果的签名输出的排序器角色**，而[拟议架构](../../meetup_record/rotation_overview.jpg)把交易排序与执行分开。
这种拆分会引入新的协议接口和责任；仅仅轮换现有签名密钥，并不能定义这些接口与责任。

## 如何理解本文的证据标签

**资料参考日期：2026 年 9 月 16 日。**
本地规格引用基于 `megaeth_specs` 的提交 `59797b45b1f59b7c2c147e6f99be39399a1f2b44`，提交日期为 2026 年 9 月 14 日。
以下标签用于区分已有证据与设计工作：

| 标签 | 含义 |
| --- | --- |
| **规格已规定** | 本地规格快照明确规定的行为。 |
| **官方文档描述** | 当前官方公开文档描述的行为；尚未通过链上数据或运行中的程序独立核实部署细节。 |
| **OP Stack 基线** | 继承自 OP Stack、或用于与之比较的背景规则；仍需考虑 MegaETH 的具体改动与配置。 |
| **推断** | 基于 OP Stack 基线或已描述的 MegaETH 架构所作的工作性还原；需要对照 MegaETH 的具体规则确认。 |
| **设计建议** | 来自会议草图或本文据此推导的设计要求，并非现有协议已经提供的保证。 |
| **待确认** | 现有证据不足以确定答案。 |

本地[Rollup 概览](../../megaeth_specs/specs/rollup/overview.md)说明 MegaETH 继承 OP Stack 的结算架构，但各个具体的 Rollup 页面目前都还只是待补全的占位页。
[无状态验证](../../megaeth_specs/specs/protocol/stateless-validation.md)同样尚未写明，[SequencerRegistry](../../megaeth_specs/specs/system-contracts/sequencer-registry.md)也只有占位内容。
因此，这份规格对 L2 传输格式的定义，远比对结算机制和权限更新机制的定义完整。
页面头部的 Rex5 元数据说明适用的规格版本，并不能证明某个网络已经激活该版本。

## 1. 基本构件与组件

### 简明术语表

| 术语 | 本文中的含义 |
| --- | --- |
| 交易（transaction） | 请求执行的一次状态转换，例如转账或合约调用。 |
| 回执（receipt，也称交易收据） | 记录执行成功或失败、gas 消耗和日志的执行输出；它不是执行后完整的状态。 |
| 状态增量（state delta） | 账户或存储的变化，接收节点可以据此更新自己的状态。 |
| Mini-block | 一个 EVM 区块内部有序的一部分，带有对交易和回执的承诺。 |
| EVM 区块（EVM block） | 容纳 mini-block 的以太坊格式区块，包含父区块哈希，以及汇总后的交易、回执和状态承诺。 |
| L1 来源区块（L1 origin） | 在 OP Stack 基线中，与某个 L2 区块所属排序 epoch 关联的以太坊区块。 |
| 批次（batch） | 为后续重建链而编码的交易输入；它与执行结果不同。 |
| 数据可用性（data availability，DA） | 能够获取重建和检查链所需数据的能力。 |
| 派生（derivation） | 根据 L1 及其引用的可用数据，重建规范的 L2 输入序列。 |
| 状态／输出提议（state/output proposal） | 提交给结算机制的声明，说明执行某一段链所得到的结果。 |
| 预确认（preconfirmation） | 排序器作出的早期承诺，其确切保证必须明确说明；它不自动等同于 L1 最终性。 |

Mini-block 和状态相关术语依据[区块](../../megaeth_specs/specs/protocol/blocks.md)、[状态同步](../../megaeth_specs/specs/protocol/state-sync.md)与 [SALT](../../megaeth_specs/specs/protocol/salt/overview.md)。
L1 来源区块的定义依据 [OP 术语表](https://specs.optimism.io/glossary.html#l1-origin)。

### 先拆分职责，再讨论由谁运行

**规格已规定：** 排序器是一个对外可见的角色。
它提供供其他节点使用的、带签名的 mini-block 和 EVM 区块。
该角色究竟由一台机器、一个备用集群，还是多个内部进程实现，不属于协议边界内的问题。
MegaETH **没有**规定类似以太坊 Engine API 的共识层／执行层接口。
[来源：排序及其范围边界](../../megaeth_specs/specs/protocol/sequencing.md#block-production-mechanics)。

**官方文档描述：** RPC 端点接收用户交易，再转发给排序器，由排序器排序并执行。
副本 RPC 节点直接应用流式传输的结果，无需重新执行；全节点则独立执行区块。
公开文档还描述了高可用备用节点、以 EigenDA 为后端的批次提交器，以及基于 Kailua 的争议证明机制。
这些是架构描述，不能据此认定系统已经具有去中心化的领导者选举协议。
[来源：MegaETH 架构](https://docs.megaeth.com/architecture)。

设计轮换机制时，即使同一个运营方承担多项工作，也应保留以下逻辑上的职责区分：

| 职责 | 它回答的问题 |
| --- | --- |
| 排序 | 在什么区块上下文中，按什么顺序放入哪些交易？ |
| 执行 | 执行该序列后，会产生什么回执与状态变化？ |
| 流式传输 | 消费这些结果的节点如何快速收到经过身份与内容认证的结果？ |
| 验证 | 这些结果是否是对已接受输入的正确执行？ |
| 批次发布 | 哪些输入能够经由结算路径被获取和恢复？ |
| 状态提议 | 向结算合约声明了什么执行结果？ |
| 挑战／证明 | 如何检查有争议的执行声明？ |
| 权限管理 | 谁有权发出每一种承诺？ |

这是为了设计而作的职责拆分，并非声称已部署的网络中存在八个独立运营方。
尤其是，讨论草图最下方的方框时，“proposer”应当指**状态提议者**；如果也用这个词指代负责排序的领导者，就会掩盖两种不同职责。

## 2. 区块结构：EVM 区块中的 mini-block

Mini-block 是 **MegaETH 特有**的结构；OP Stack 提供了有用的结算背景，但没有定义 MegaETH 的 mini-block 格式。
这两种区块格式在本地[区块与 mini-block 规格](../../megaeth_specs/specs/protocol/blocks.md)中都有定义。
下表区分了区块头中的承诺，以及这些承诺所对应的实际数据。

| 特征 | Mini-block | 容纳它的 EVM 区块 |
| --- | --- | --- |
| 身份标识 | 所属 EVM 区块的 `block_number`、区块内的 `index`，以及整条链范围内的 mini-block `number` | EVM 区块编号与区块哈希 |
| 位置／链接 | 没有父区块哈希；通过有序传输及所属 EVM 区块的上下文检查其位置 | 区块头包含 `parent_hash` |
| 时间 | `block_timestamp` 是所属 EVM 区块以秒为单位的时间戳；从 Rex5 开始，`timestamp` 使用微秒 | 区块头的 `timestamp` 使用秒 |
| 交易 | 包含有序交易列表；区块头中的 `tx_root` 对其作出承诺 | 区块体中的交易列表是所有 mini-block 交易列表按顺序拼接的结果 |
| 回执 | Mini-block 体包含回执；区块头中的 `receipt_root` 对其作出承诺 | 汇总后的回执列表在区块头中有对应承诺；回执是执行输出，而不是普通的区块体交易 |
| Gas | `gas_used` 是该 mini-block 内各交易总 gas 消耗之和 | 区块头记录整个区块的 gas 消耗及区块 gas 上限 |
| 状态 | Mini-block 头没有状态根；状态增量通过状态同步单独传输 | 区块头包含从 MegaETH 的 SALT 状态得出的 `state_root` |
| 日志 bloom | Mini-block 头没有 bloom 过滤器；回执携带各自的 bloom | 以太坊格式的区块头包含日志 bloom |
| 其他头部字段 | 严格限于下文列出的八个字段 | 以太坊／OP 格式的字段，其分叉相关语义由相应规则决定 |

每笔交易恰好属于一个 mini-block 和一个 EVM 区块；任何 mini-block 都不能跨越 EVM 区块边界。
每个 EVM 区块至少包含一个 mini-block。
进入下一个 EVM 区块时，`index` 重置为零，而整条链范围内的 mini-block 编号持续递增，不会重置。
例如，区块 `1200` 可以依次包含交易列表 `[a,b]`、`[c]` 和 `[d,e]`，那么该 EVM 区块的交易列表就是 `[a,b,c,d,e]`。
其交易根是在这个完整列表上重新计算的，**不是**把三个 mini-block 的交易根组合起来。
回执根也有同样的区别。

状态增量并不是 mini-block 头的第九个字段。
[状态同步](../../megaeth_specs/specs/protocol/state-sync.md#streams-and-payloads)会单独传输状态增量，并将其绑定到重建出的 EVM 区块。
回执中的 gas 计数器在整个 EVM 区块范围内累计，因此计算 `[d,e]` 所消耗的 gas 时，需要使用前面的累计值，不能在每个 mini-block 开头重新计数。
[来源：mini-block 组装](../../megaeth_specs/specs/protocol/state-sync.md#mini-block-assembly)。

### Mini-block 签名究竟承诺了什么

从 Rex5 开始，带签名的 mini-block 头承诺以下八个字段：

```text
block_number, block_timestamp, index, number,
timestamp, gas_used, tx_root, receipt_root
```

签名覆盖 `keccak256(rlp(header))`，从签名恢复出的密钥必须是 `sequencerAt(block_number)` 返回的密钥。
同一个 EVM 区块中的所有 mini-block 使用同一把获授权的密钥；待生效的密钥变更会在后续某个区块开始之前生效。
[来源：mini-block 头签名](../../megaeth_specs/specs/protocol/blocks.md#mini-block-header-signing)、[排序器权限](../../megaeth_specs/specs/protocol/sequencing.md#sequencer-authority)。

这立即带来三个重要结论：

1. **该签名同时承诺排序与执行结果。**
   仅凭交易排序无法得到 `receipt_root` 与 `gas_used`。
2. **该头部既不包含父区块哈希，也不包含状态根。**
   位置与链接关系依赖外围协议和所属 EVM 区块；它并不是一条由微型以太坊区块头组成的、自包含的链。
3. **可归责性、正确性和最终性是不同的性质。**
   签名识别了可追责的密钥，并绑定签名内容，但不能证明执行正确，也不能证明 L1 最终会保留这些交易。

[区块规格](../../megaeth_specs/specs/protocol/blocks.md#security-considerations)明确提醒，不应把签名当作最终性。
同样，文档即使描述了如何证明双重签署，也不意味着已部署的合约会自动对其进行罚没。

## 3. 出块规则

### 3.1 接收、准入与执行是不同的检查

交易池通常称为 mempool，是出块者保存待处理请求的集合。
**推断的运行模型：** RPC 接收请求并将其存入交易池，发生在最终准入区块之前；但这两步都不构成协议必须纳入该请求的承诺。
本地规格没有定义一个全局一致的 mempool，也没有要求每个候选排序器都看到完全相同的待处理交易。

对于普通交易，签名、nonce 和余额必须在该交易所处的位置、基于区块内不断演进的状态满足准入条件。
如果某账户的下一个 nonce 是 `7`，nonce 为 `8` 的交易不能直接先执行；前序交易可能推进 nonce，也可能消耗后续交易所需的资金。
这来自[排序规格](../../megaeth_specs/specs/protocol/sequencing.md#transaction-admission-and-ordering)中列出的普通有效性检查。
因此，一份带签名的排序列表不能把交易有效性视为与所选历史前缀无关。

有效交易仍然可能**在执行时回滚（revert）**：例如，一笔兑换交易的最低输出数量条件可能无法满足。
此时回执报告失败，但该交易仍然占据区块中的相应位置。
这与不满足准入条件的交易不同：后者依据适用的交易规则，根本不能被放入该位置。
仅负责排序的设计，需要先区分这两种情况，再定义“执行器必须遵守排序”意味着什么。

### 3.2 强制前缀与普通交易的排序

**规格已规定：** 每个 EVM 区块的第一个 mini-block，必须将所有被提供的存款交易和 L1 属性交易置于普通交易之前。
除此之外，普通交易的排序策略不受约束：规格没有承诺按到达顺序排列，也没有承诺公平性或纳入某个 RPC 节点看到的每一笔交易。
验证关注的是交易是否满足准入条件、状态转换是否正确，而不是重现排序器采用的调度策略。
[来源：交易准入与排序](../../megaeth_specs/specs/protocol/sequencing.md#transaction-admission-and-ordering)。

存款交易与 MegaETH 系统交易都需要与普通用户交易区别对待。
其中，系统交易通过交易格式、系统签名者及获准的目标地址识别，具有特殊的费用与 nonce 语义。
关键是，**系统地址的轮换独立于 mini-block 签名密钥的轮换**。
未来的轮换协议必须说明它是否改变这两种权限中的任何一种，不能假设两者总是一起变更。
[来源：交易类型与签名者权限](../../megaeth_specs/specs/protocol/transactions.md)。

### 3.3 来源区块与时间约束

**OP Stack 基线：** 每个 L2 epoch 标识一个 L1 来源区块；该来源区块中的存款、属性、符合条件的批次，以及此前的 L2 状态，共同决定派生过程。
基线对时间戳有以下要求：

```text
t = previous_L2_timestamp + block_interval
t >= origin_timestamp
if t > origin_timestamp + drift_bound:
    ordinary_sequencer_transactions = []
```

这些是必要的时间条件，并不是完整的批次接受算法。
即使排序器批次为空，在超过漂移上限后，如果采用下一个来源区块不会违反最低时间戳规则，就不能继续保留旧的来源区块。
来源区块哈希必须与规范 L1 区块一致，来源区块的推进方式也受到约束。
这里的时间间隔指 EVM 区块间隔，不是 mini-block 间隔。
[来源：OP 派生规则](https://specs.optimism.io/protocol/derivation.html#overview)。

**推断的 MegaETH 要求：** 来源区块的选择必须满足继承的来源区块／时间规则，以及 MegaETH 对这些规则所作的改动，不能任意挑选历史 L1 区块。
由于本地[派生规则改动说明](../../megaeth_specs/specs/rollup/derivation.md)尚未完成，确切的来源区块推进规则、漂移参数及批次接受条件仍未核实。

### 3.4 资源限制与封块

**官方文档描述：** MegaETH 区分准入时的限制与执行时的计量规则。
资源维度包括总 gas、计算 gas、传输数据量、键值更新量、状态增长量、编码后的交易大小，以及 DA 数据大小。
有些超限请求在进入区块前就会被拒绝；另一些执行过程中的超限情况，则会产生一笔已经纳入区块、但回执报告失败的交易。
对于区块级的数据大小、键值更新量与状态增长量，文档描述的构建器可以纳入最后一笔使计量值跨过阈值的交易，然后停止继续添加交易。
因此，仅凭“这个区块超过了某个资源数值”，还不足以判断区块无效；必须先检查该资源的具体计量规则。
本文不假定任何部署中的具体数值限制。
[来源：MegaETH 资源限制](https://docs.megaeth.com/developer-docs/overview-3/resource-limits)。

**规格已规定：** 每个 EVM 区块至少需要一个 mini-block，但 mini-block 数量与封块节奏属于实现策略。
公开的 [mini-block 指南](https://docs.megaeth.com/mini-block)描述了约 10 毫秒的 mini-block 和 1 秒的 EVM 区块；这种运行节奏并不是要求每个 EVM 区块恰好包含 100 个 mini-block 的有效性规则。
Mini-block 的实际时钟时间戳不要求单调递增；顺序由 `index` 和 `number` 决定。
[来源：出块机制](../../megaeth_specs/specs/protocol/sequencing.md#block-production-mechanics)、[时间戳语义](../../megaeth_specs/specs/protocol/blocks.md#mini-block-timestamps)。

## 4. 完整生命周期：从用户请求到结算声明

### 4.1 接收请求、选择上下文、执行与封块

出块者收到候选请求后，按照第 3 节的规则选择有效的区块上下文和满足准入条件的交易序列，执行交易，并生成第 2 节介绍的结构。
随着 mini-block 逐个形成，回执与状态增量也逐步可用。
这是低延迟路径；发布与结算会在之后推进。
下文各步骤描述的是逻辑依赖关系，并不要求一个线程或一个运营方将所有工作串行完成。

### 4.2 流式传输结果与重建状态

**规格已规定：** 状态同步传输四条分别进行认证的数据流：状态变化、交易、回执与 EVM 区块头。
前三条数据流针对每个 mini-block 分别提供一个片段；最后一条提供已经封好的 EVM 区块头及元数据。
接收方根据各片段重建 mini-block 头，再针对这个重建结果验证 mini-block 签名。
[来源：数据流与组装](../../megaeth_specs/specs/protocol/state-sync.md#streams-and-payloads)。

这里存在两个不同的签名层次。
Mini-block 头签名使用前文所述的 keccak 摘要；数据流载荷认证则使用基于 BLAKE3 的哈希，并把载荷内容绑定到它在流中的位置及区块编号。
检查历史载荷时，应使用在其所属区块获授权的密钥，而不是下载时碰巧正处于生效状态的密钥。
[来源：载荷认证](../../megaeth_specs/specs/protocol/state-sync.md#payload-authentication)。

组装 EVM 区块时，接收方检查父区块链接、汇总后的交易根与回执根、合并后的 SALT 状态增量承诺，以及应用这些增量后得到的状态根。
这些检查能够发现传输内容的不一致或损坏。
但它们**不能**独立证明这些状态增量确实来自对交易的正确 EVM 执行：恶意排序器可以为彼此一致、但执行结果错误的输出签名。
[状态同步的信任模型](../../megaeth_specs/specs/protocol/state-sync.md#trust-model)明确说明了这个区别。

相比之下，基于 witness 的验证者需要足够的、经过认证的执行前状态信息，才能重新执行并比较所得输出。
[SALT witness](../../megaeth_specs/specs/protocol/salt/witness.md)规定了经过认证的状态信息，但完整的[无状态验证流程](../../megaeth_specs/specs/protocol/stateless-validation.md)仍未写明。
因此，“副本收到了结果”“验证者检查了执行”和“结算机制接受了结果”是三个不同的里程碑。

### 4.3 经由 DA 与 L1 发布可重建的输入

**官方文档描述：** MegaETH 将批次数据发送至 EigenDA，并通过 L1 提交路径发布对应的 DA 证书。
官方集成说明区分了分布式 blob 存储与体积较小的链上引用；以太坊不需要把完整的批次字节存放在自身的执行存储中。
[来源：MegaETH 与 EigenDA 的集成](https://www.megaeth.com/blog-news/endgame-how-we-break-performance-limits-with-eigenda)。

**OP Stack 基线：** 批次提交器将 L2 输入打包以便发布，其中涉及压缩以及 channel／frame 处理。
这是一项输入发布工作，与状态提议者提交执行声明不同。
[来源：OP 批次提交器](https://specs.optimism.io/protocol/batcher.html)。

**待确认：** MegaETH 的[批次提交占位页](../../megaeth_specs/specs/rollup/batch-submission.md)提到了提交前的验证关卡，但没有定义其算法，也没有说明提交范围以哪个已验证的链头为界。
[DA 占位页](../../megaeth_specs/specs/rollup/data-availability.md)同样未规定证书有效性、数据获取失败和 DA 服务中断的处理方式。
不能仅凭这些页面标题，就假设每个已经发布的区块都通过了某个特定验证者法定人数的检查。

证书、获取到的字节与执行有效性，是三个不同的对象。
对于轮换机制，实际问题是：接替者能否获取延伸已接受历史前缀所需的全部输入，包括已经作出早期承诺、但尚未完成持久发布的输入。
如果只有对不可获取字节的签名，并不能获得这种能力。

**OP Stack 基线：** 执行过程应用派生出的输入，得到状态；批次本身不携带 EVM 区块的执行承诺。
L1 重组可能改变派生结果，使其与低延迟数据流不一致。
[来源：OP 派生流程](https://docs.optimism.io/op-stack/protocol/derivation-pipeline)。
这里描述的是面向结算的数据依赖关系，并不是要求 MegaETH 在内部必须拆分共识层与执行层。

### 4.4 提议状态、解决争议与支持提款

**OP Stack 基线：** 状态提议者提交一个承诺，声明执行某段明确的 L2 历史所得的结果。
输出承诺可能不只包含状态根：OP 的构造还绑定了与提款相关的状态，以及一个 L2 区块哈希。
在检查 MegaETH 对 SALT 和结算机制所作的适配之前，不能将这些具体字段直接照搬过来。
[来源：OP 输出承诺](https://specs.optimism.io/protocol/proposals.html#l2-output-commitment-construction)。

**官方文档描述：** MegaETH 关于 ZK 欺诈证明的说明，描述了对“从某个初始状态执行某份载荷”的结果作出乐观声明，再使用简洁证明解决对结果的分歧。
它描述的是乐观挑战模型，并非要求每个普通状态提议都附带有效性证明。
该文章发表于 2025 年 7 月 23 日；本文没有独立核实其中的时间与罚没表述是否属于实际部署参数。
[来源：MegaETH 的 ZK 欺诈证明说明](https://www.megaeth.com/blog-news/endgame-how-we-use-zk-to-secure-megaeth)。

Kailua 本身目前支持混合模式与有效性模式，因此它所具备的功能，并不能决定某个 MegaETH 部署实际使用哪种模式。
[来源：Kailua 仓库](https://github.com/boundless-xyz/kailua)。
本地[错误证明页面](../../megaeth_specs/specs/rollup/fault-proofs.md)尚未明确具体的提议／挑战流程与裁决规则。
所以，草图中的 **“state root + proof”** 箭头应被理解为尚待确定的接口：必须说明证明是随每次提议一起提交、只在争议时生成，还是承担其他作用。

**OP Stack 基线：** 提款首先在 L2 的 Message Passer 中记录一条消息，随后在 L1 上针对一个已接受的输出承诺证明该消息的存在，最后只有满足相应结算条件后才完成最终确认。
[来源：OP 提款](https://specs.optimism.io/protocol/withdrawals.html)。
较新的错误证明桥接集成采用争议博弈，取代旧版输出预言机，并引入博弈裁决与成熟期条件。
因此，一份旧的 `L2OutputOracle` 教程不足以证明今天的 MegaETH 提款路径是怎样的。
[来源：OP 桥接集成](https://specs.optimism.io/fault-proof/stage-one/bridge-integration.html)。
MegaETH 的[提款改动说明](../../megaeth_specs/specs/rollup/withdrawals.md)，包括 SALT 证明在内，目前仍然只是占位页。

### 4.5 按步骤追踪一笔交易

假设 Alice 提交了一笔设有最低输出数量约束的兑换交易。
以下数字仅用于示例标识，不是网络参数。

1. **纳入区块之前：** RPC 确认收到请求，意味着她的请求已经到达。
   它并没有确定交易的最终位置，也不承诺执行成功。
2. **排序与执行时：** 出块者把这笔兑换交易放入 mini-block `(1200, 3)`，在前序交易之后执行。
   先前的一笔兑换可能改变池子价格；Alice 的调用可以合法地回滚，同时仍然被纳入一个有效区块。
3. **早期结果传输时：** Alice 收到回执、状态更新及经过认证的承诺。
   她可以检查获授权的签名者是否承诺了这些结果；独立检查执行是否正确则是另一项工作。
4. **组装 EVM 区块时：** 区块 `1200` 承诺按顺序拼接的交易与回执，以及执行后的状态。
   接收方检查它与 mini-block 数据流是否一致。
5. **发布到 DA 时：** 批次字节被分散存储，并通过证书引用。
   验证者仍然需要获取并检查实际字节，而不是“执行证书”。
6. **被 L1 纳入并进行派生时：** 一个被认可的批次提交在以太坊上引用这些输入；验证者据此派生并执行相关历史。
   这一步开始通向第 5 节所述、能够独立派生的安全链。
7. **L1 最终确认时：** 派生所依赖的 L1 历史获得最终性，但仍受以太坊最终性与外部 DA 假设的约束。
8. **状态声明结算时：** 一个覆盖该段历史的提议，经过适用的证明／争议规则后被接受。
   提议的提交不一定要等本教学列表中的所有前序步骤都完成；具体争议博弈的前置条件决定实际时序。
9. **之后需要提款时：** Alice 发起 L2 提款，针对一个符合条件的输出证明其包含关系，然后完成单独的 L1 最终确认流程。
   她原来的兑换交易本身不要求提款。

现在假设在第 3 步之后、第 5 步之前发生轮换。
对于接任的排序者，仅知道区块 `1200` 有一个获授权的签名者并不够：它需要经过认证的已承诺历史前缀、相关有序输入、区块上下文，以及执行器经过认证的进度，才能知道从哪里恢复排序。
接替的执行器或完整出块者还需要执行状态，或者能够重建状态的检查点；接管发布工作的角色则需要尚未提交的批次积压数据。
如果接替者直接另起一个不同的区块 `1200`，Alice 手中的承诺可能是真实的，却未被最终形成的链履行。
这个例子是在分析上述承诺对设计提出的要求，并非声称今天的高可用系统采用了这一流程。

## 5. L1 确认与数据可用性

### 5.1 这里说的是哪一种确认？

**OP Stack 基线：** 独立进行派生的节点区分以下几类链头。
下表术语依据 [OP Stack 交易最终性](https://docs.optimism.io/op-stack/transactions/transaction-finality)；要将其用于 MegaETH，必须结合 MegaETH 的外部 DA 规则。

| 里程碑 | 已经确认的事情 | 单凭该里程碑还不能确认的事情 |
| --- | --- | --- |
| Mini-block 承诺 | 某把获授权的密钥对特定内容进行了签名 | 执行正确、持久发布，或 L1 最终性 |
| 不安全 EVM 区块（unsafe） | 出块者在 L1 确认之前提供了一个 L2 区块 | 同一个区块一定能从规范 L1 历史中派生出来 |
| 安全 L2 区块（safe） | 节点从当前规范 L1 历史中已接受的数据派生出了该区块 | 支撑它的 L1 历史不会发生重组 |
| 已最终确认的 L2 区块（finalized） | 所需的 L1 历史已经获得最终性 | 桥接所需的独立输出声明与提款条件已经满足 |
| 已结算的输出声明 | 相应结算机制接受了一项执行声明 | 某笔具体提款已经完成证明与最终确认 |
| 已最终确认的提款 | 桥已完成必要检查与 L1 操作 | 对无关交易或后续区块的保证 |

**规格已规定的限制：** MegaETH 的状态同步元数据包含 `safe` 与 `finalized` 标记，但它们代表的是排序器报告的视图。
副本收到这些标记，并不意味着它已经验证了 L1 最终性。
[来源：区块元数据](../../megaeth_specs/specs/protocol/state-sync.md#block-metadata)。
选择接管检查点时，这一点很重要：发生故障的领导者提供的标签，与独立派生得到的检查点，是不同类型的证据。

在 OP Stack 基线中，挑战错误的输出声明不会重写正确派生的 L2 链；它否定的是对该链所作的错误结算声明。
因此，通常提到的提款等待时间与交易最终性并不是同一件事。
[来源：OP Mainnet 关于最终性的说明](https://docs.optimism.io/op-mainnet/network-information/transaction-finality)。
不能把其中的具体时间参数直接套用于 MegaETH。

### 5.2 DA 证书能做什么，获取数据又需要什么

**DA 背景：** EigenDA 白皮书区分了分散存储字节、验证证书、获取字节，以及观察数据可用性这几件事。
其保证依赖存储节点的诚实阈值、可访问的数据获取路径，以及明确的数据可用时间窗口。
验证证书是密码学检查，而获取数据是网络操作；证书不等于无限期存储，也不能证明 EVM 执行正确。
[来源：EigenDA 白皮书第 1、3 节](https://docs.eigencloud.xyz/assets/files/EigenDA_Whitepaper-c917fb56c146ebd146abfba3c52648a1.pdf)。

**推断的 MegaETH 流程：** 派生节点遇到一个被接受的 L1 引用后，检查适用的证书规则，获取被承诺的批次字节，检查字节与承诺的绑定关系及其编码，然后派生 L2 输入。
这是根据官方描述的 EigenDA 集成与 OP 派生基线作出的自然还原，并不是已经完成的 MegaETH 规范算法。
[DA](../../megaeth_specs/specs/rollup/data-availability.md)与[派生](../../megaeth_specs/specs/rollup/derivation.md)占位页尚未说明其中各类失败应如何处理。

设计时至少应明确区分三种结果：证书格式错误或无效；证书看起来有效，但当前无法获取其对应的字节；字节可以获取，但解码后是无效批次。
它们不一定触发相同的处理动作。
临时的数据获取失败，不能在没有明确规则的情况下赋予接任者权力，允许它在已经承诺的位置编造不同交易。
同样，包含证书的以太坊交易获得最终性，也不能独立证明每个挑战者都已经取得了外部字节。

### 5.3 一个可用于研究的 OP 衍生后备路径假设

OP 的[派生流程说明](https://docs.optimism.io/op-stack/protocol/derivation-pipeline)描述了这样一种情况：排序窗口到期后仍没有有效批次，系统便以仅含存款的输入继续推进，并丢弃与之不兼容的 unsafe 历史。
**推断的研究基线：** MegaETH 可能保留了类似的、由 L1 驱动的退出受阻状态的路径，这与其公开的强制纳入文档相符。
其中涉及的外部 DA 超时、具体接受条件与恢复实现，仍需确认。
应当把它视为检查设计时使用的假设，而不是已经确立的后备算法。
这也意味着，除非轮换机制确保及时发布，否则某些普通交易的早期承诺可能无法进入派生出的链。

## 6. 拟议的仅负责排序的排序器会改变什么

[会议草图](../../meetup_record/rotation_overview.jpg)将交易选择、纳入、排序和来源区块选择交给排序器，而由预确认器执行、提供结果并发布批次。
现有 mini-block 签名不能简单改名为排序签名，因为它已经覆盖回执与 gas。

| 草图中的要素 | 必须作出的设计决定 |
| --- | --- |
| 排序器为交易列表签名 | 定义签名覆盖的上下文、交易编码、位置、来源区块、前驱承诺及权限 epoch。 |
| 排序器无需执行 | 定义如何处理 nonce／余额冲突、资源耗尽，以及在签名指定位置无法满足准入条件的交易。 |
| 预确认器执行给定顺序 | 规定它能否拒绝整个列表、按照确定性规则略过某些条目，或请求替换列表；不作说明、凭自由裁量修改列表，会破坏排序承诺。 |
| 用户验证排序器签名 | 单独认证执行声明，并规定用户如何检查执行声明与签名排序之间的关系。 |
| 预确认器发布批次 | 将发布内容绑定到已接受的顺序，定义期限，并决定是否允许其他发布者在其故障后接管。 |
| 状态提议者提交结果 | 将其声明绑定到规范输入序列，包括任何获准的无效条目处理规则。 |
| 另一个排序器接管 | 依据明确的权限规则，选出唯一接任者，并确定唯一要继承的历史前缀。 |

这些是拟议的要求，并非对现有协议行为的补充描述。
其中一些要求可以在保留当前“单个活跃出块者”抽象的情况下满足；但如果对外引入可分别追责的排序者与执行器，其他节点必须验证的内容就会改变。

现有以区块边界为准的权限规则还带来一个具体约束：若要在一个 EVM 区块中途切换 mini-block 签名密钥，就必须修改该规则。
另一种方式是在 EVM 区块边界使轮换生效，同时用单独的恢复流程处理未完成的区块。
要在这两种方式之间作选择，就必须明确哪些早期承诺在故障后仍然有效。

最后，仅更换负责排序的角色，无法修复停滞的执行器、缺失的 DA 发布，或没有提交结果的状态提议者。
每个依赖环节都需要自己的恢复路径，或者需要明确假定它一直可用。

## 7. 选择轮换协议之前，还需要哪些背景

官方[强制纳入指南](https://docs.megaeth.com/user-guide/force-inclusion)描述了通过以太坊上的 portal 提交交易、绕过排序器的方式，并给出了 12 小时内纳入的上限。
在检查已部署配置及故障行为之前，应将它视为官方文档面向用户给出的声明；本地[存款／强制纳入规格](../../megaeth_specs/specs/rollup/deposits.md)并没有提供相关机制或证明。
即使确实存在一条较慢的 L1 后备路径，也不足以说明系统能够达到草图所追求的快速恢复目标。

下一轮实现审查需要解决以下具体缺口：

- **权限：** 谁能安排 registry 变更，接收方如何认证 registry 状态，以及变更如何与 L1 重组相互作用。
- **发布：** 谁控制批次提交权限，提交前的验证关卡检查什么，以及接任者能否发布继承的数据。
- **执行：** 在仅负责排序的承诺变得具有约束力之前，适用哪些准入与资源规则。
- **恢复：** 接任者必须保留哪一段带签名的历史前缀，以及对应数据不可获取时如何处理。
- **结算：** 实际部署的争议博弈类型、提议权限、保证金、证明程序、挑战条件与提款成熟期规则。
- **故障语义：** 缺少 DA 证书、blob 无法获取、排序器中断，或状态提议者停止提交时，系统实际上如何运行。

对应会议中的问题，第 1—5 节分别覆盖组件、区块结构、出块规则、完整生命周期，以及 L1 确认与 DA。
第 6 节指出拟议的职责拆分引入了哪些变化，第 7 节则列出在赋予系统活性或有效性保证之前仍需取得的证据。
配套的需求与文献笔记，便可以据此对照具体流程来比较不同轮换机制。
