# v3.8 candidate: one regional INPUT_REPORT certificate for term-first DATA

Status: constructive design for the next numbered candidate, not an independent verification or a completed arbitrary-membership request-liveness theorem. This note does not edit existing manuscript sources; its companion implementation text is the new `sections/rotation_v3_8_requests.tex` fragment. The candidate explicitly changes the request-selection algorithm and regional validation. It keeps the v3.1 environment assumptions and the original complete publication-result interface. The separate obligation to deliver a retained request to the relevant correct members of changing rosters remains open here; it must be supplied by a proved node-level dissemination construction, not by interpreting “region” as an immortal omniscient process.

The useful conclusion is that **AcquirePending is unnecessary**. Once a member has the exact first-DATA parent, its own retained eligible minimum suffices for its report. Ordinary terms obtain their first DATA votes within `4 Delta` of first correct entry; initial/recovery term zero retains `6 Delta`. A valid accepted first-DATA witness containing an aware correct report spends one previously unaccepted member of a fixed finite predecessor set. Speculative commits and Force cannot replenish that set because its potential is measured only on `G`.

Source names below mean the live files under `formalization_v2/`: `main` is `sync_hotstuff_rr_part2_rotation_v3_7.tex`; `kernel` and `live` are `sections/rotation_v3_7_receipt_kernel.tex` and `sections/rotation_v3_7_liveness.tex`; `Part I` is `sync_hotstuff_rr_part1_core.tex`. The adjacent `request_report_scope_analysis.md` and `request_report_carriage_design.md` explain the earlier conditional query design and the full-public-result/sidecar distinction.

## 1. Algorithmic scope and the two result types

Replace the oldest-pending rule for the first DATA position of each DATA-producing term by the mandatory primary rule below. After that primary, and at every later position, use the existing local first-receipt FIFO filling rule. Thus the algorithm supersedes the relevant correct-leader batching clause of Part I `ass:fairness` and `main:2221–2239`; it does not claim to preserve that clause unchanged. Schedule fairness, request ingress, synchrony, cryptographic premises, fixed membership within a session, and global-prefix retention are unchanged.

Retain the original public input type explicitly:

- `R0`: the complete old-format regional result, including **all** original required DATA, FINAL, proposals, QCs, ancestry, boundary, authority, native-validation and public-source material.
- `R+ = (R0, WR)`: a regional complete bundle adding the INPUT_REPORT certificates required by augmented own-session validation.

All regional Vote, own-session recovery, own-session receipt/Completion, evidence-serving and retirement paths use `R+` where the added predicate applies. The Publish Layer receives `R0`, the whole original logical result, with its original public denotations. Public `CheckFINAL` remains unchanged. Section 8 proves why these interfaces are consistent; this is never a license to publish only `K(R0)`.

The candidate is specified for sessions whose correct members all run this algorithm. An upgrade boundary between old and new software would require a separate authenticated activation specification. Unchanged FINAL bytes alone cannot retroactively establish enforcement by an old session.

## 2. Request identity, order, and the local index

Let `id(x)` be the logical client request identity and `enc(x)` its canonical authenticated request representation. Re-delivery, alternate transport wrappers and alternate encodings of the same authentication proof do not create a fresh logical request. An application must identify exactly which fields distinguish a new command from retransmission. Use canonical body/authentication normalization already required to compare requests, or define it explicitly as part of this algorithm.

Define

`key(x) = (len(enc(x)), H(enc(x)))`,

ordered lexicographically, with `EMPTY` greater than every request key. Hash binding identifies the actual represented request; in the collision-free executions admitted by the existing cryptographic abstraction, distinct actual canonical bodies have distinct keys. The finiteness argument below uses finite strings of bounded length, not an assumed arrival order or a claim about the number of hash outputs generated by an infinite execution. If two authenticated body variants share a logical identity, ancestry exclusion excludes both after either identity occurs; this only strengthens the bound.

For a completely validated parent `P` and node `v`, define

`Eligible_v(P) = {x retained at v : x is admissible immediately after P,
                 x fits alone in a DATA batch, id(x) is absent from Anc(P)}`.

`Anc(P)` includes the inherited prefix and the full exact speculative ancestry of `P`, not merely locally committed or accepted blocks. Eligibility is evaluated before adding any other request to the new batch. Native validation and the exact usable parent state are the existing inputs to building a valid batch.

The local state has a request table keyed by logical identity, an ordinary first-receipt FIFO index, and a key-ordered index of the same retained requests. For each exact parent currently being processed, its eligible projection records the minimum or `EMPTY`. Process a complete parent/request event in this order:

1. Authenticate and install the exact parent history/native-validation state needed by the old batch builder.
2. Apply ancestry exclusion and the existing application-admission checks to the retained candidates in key order; materialize the eligible projection or compute its first eligible entry.
3. Complete that handler, then execute any enabled report/proposal action using that projection.

New requests update the retained table and relevant index; `G` inclusion authorizes final deletion. Discarding a speculative suffix changes parent eligibility, not retained ownership. A cached projection is keyed by the exact parent hash/state and cannot be reused for a different parent.

**Processing scope.** This is an explicit local selection algorithm, not a mempool acquisition service. It introduces no wait for remote pools, cross-region discovery, or a complete inventory of all client requests. In the manuscript's abstract event model, selection uses the same batch-construction operation that already chooses pending admissible requests after the parent. Parent-dependent filtering is part of the completed message/batch-processing event, rather than a newly deferred task after the event has been declared complete. A maintained index makes selection explicit; it does not prove that an arbitrary native admission predicate can be updated in constant wall-clock time.

Consequently the timing lemmas below have the **same abstract processing scope as the existing correct-leader proof**, whose “build batch” action has no separately charged local-computation latency and whose complete-message bound includes validation dependencies (`main:392–404,941–955`). They add no independent bound on whole-pool scanning, native import or deployed CPU/load. If a concrete implementation places an unbounded eligibility rebuild, queued callback or state import outside that completed handler, the old `Delta` timing is not established for that implementation. It must not label unfinished work a completed report event. This qualification is the original processing boundary made explicit, not a new request-acquisition assumption.

## 3. Exact report context and trigger

Let `V=(beta,r,g,t)` and let `P=A_(beta,r,g,t)` be the immutable parent of its first fresh position. The report's signed context is

```
RC = (chain_id, protocol_domain, INPUT_REPORT,
      beta, r, assigned_region, cfg_r, AUTH_(r,g)_reference,
      g, t, j=0, generation_opening_identity,
      parent_hash(P), parent_DATA_height(P), parent_physical_position(P))
INPUT_REPORT = Sign_v(RC, key(x) or EMPTY)
```

The opening identity is the existing `(g,k(A_(beta,r,g,0)),h(A_(beta,r,g,0)),H(A_(beta,r,g,0)))`. The authentic incoming boundary and immutable authority determine the roster, region, quota, initial anchor and entry context. A claimed pair or a signature over `RC` is not itself an authority proof. Redundant parent positions may be derived in serialization, but verification must check their equality to the exact parent. Alternate QC signer sets do not change `RC`.

For `t>0`, `P` is exactly the prior term's terminal DATA, certified by its terminal QC. For `t=0`, `P` is exactly the fully validated NEWVIEW opening; in generation zero it must equal the boundary's fixed initial anchor. A report cannot be created against a placeholder opening at recovery entry.

Add a durable per-context record `ReportSent[RC]`. On local ordinary-term entry, or on complete processing of the valid NEWVIEW for an entered term zero, run:

```
ReportIfReady(RC):
    require original fresh-action/retirement gate is open
    require this session/generation is entered, current and unfrozen
    require original term admission and exact first-parent validation are complete
    require this is a DATA-producing term
    if ReportSent[RC] exists: resend that same report when required; return
    y := min Eligible_v(P), or EMPTY
    persist ReportSent[RC] := Sign_v(RC, key(y) or EMPTY)
    dispatch the report to L(V), with full authenticated y bytes if nonempty
```

Ordinary entry executes the action in that entry handler. Term-zero report emission is a separate action of complete NEWVIEW processing. Preserve the original immediate ANCHOR-VOTE and NEWVIEW forwarding: neither waits for a report, a report quorum or a new query. A combined transport packet has independently parsed ANCHOR and REPORT subrecords; an invalid REPORT does not invalidate an otherwise valid ANCHOR vote or suppress embedded original Quit evidence. A correct initializer's NEWVIEW meets all correct entry locks by the original argument; the report rule does not modify those locks or the ANCHOR-vote test.

Later request arrivals do not amend the saved report, even if it was `EMPTY`. No fresh reports are manufactured while validating an archived context, after Quit/Completion/closure, or merely because a late publisher needs one. Already dispatched reports and persisted outgoing relays may be retained/served after the fresh-action gate closes. Duplicate handling is durable across restart.

The one-report restriction is per exact `RC`, not a new voting safety invariant. Different parents/openings in one view still trigger the original signed-proposal/NEWVIEW evidence checks. Reports themselves create no timer, QC rank, entry permission, commitment, public acceptance, new Quit type or slashing rule.

## 4. Collection, selection, and complete validation

At a correct leader, process original signed evidence before any wrapper rejection. For the target `RC`, accept a member's contribution for collection only after its signature, snapshot membership and exact context validate. For a nonempty contribution, obtain its complete body and locally check its key, authentication, admission immediately after `P`, individual fit and ancestry absence. Ignore malformed, mismatched, incomplete or ineligible contributions. Count each member at most once; retain one valid contribution per member for the chosen certificate. No completion obligation is assigned to a Byzantine reply.

The leader does not wait to recognize “all correct members replied.” As soon as its validated contribution set `S` has weight `>F` and it has the existing parent/ANCHOR QC, it constructs the first DATA:

```
if S has a nonempty key:
    z := request with minimum nonempty signed key in S
    batch := [z]
    fill remaining capacity by ordinary local FIFO,
        validating after the accumulated batch and excluding duplicate identities
else:
    batch := ordinary valid FIFO batch, possibly empty

build and sign the original DATA/PROPOSE object using this ordinary batch
attach sidecar Cert(RC,S), containing signed keys and member identities
broadcast the complete augmented regional validation bundle
```

For an all-EMPTY certificate, the batch may include requests received since reports were issued. `EMPTY` describes the reporter's eligible local set at its historical report event; it is not a permanent emptiness constraint on this parent. Ordinary valid batching remains possible, so stale EMPTY cannot force an honest leader to construct an invalid block.

The mandatory primary is executed first. Filling rechecks validity after the primary and each preceding fill request. A selected request that fits alone always permits at least the singleton batch. The leader must not reserve extra application bytes for REPORT; its certificate is a regional validation sidecar.

Every full regional validator checks the following for a DATA proposal at `j=0`:

1. Original full validity and genuine admission/parent context.
2. The exact `RC`, distinct member signatures from the authentic fixed snapshot, and total weight `>F`.
3. If any signed key is nonempty, the minimum signed key equals the first request's key; its complete actual body is authenticated, admissible immediately after `P`, individually fits and has no identity occurrence in `Anc(P)`.
4. The whole ordinary application batch is valid and does not repeat the selected primary identity. If every key is EMPTY, apply original batch validity; an empty batch is allowed but not required.

The minimum is mechanical over the supplied signed keys. Other validators need not receive nonselected candidate bodies or prove that a Byzantine reporter chose its own minimum. They do not consult their private queues, require their own report to occur in `S`, require a locally preferred primary, re-evaluate the report against current `G`, or impose receive-time freshness. The correct reporter's actual selection rule supplies the semantic fact used in Section 9. A selected fictitious key cannot pass the required body check; a nonselected bogus key larger than the real minimum does not falsify that implication.

For `j>0`, use original batch validity and recursively validate the required first-DATA evidence in its own-session ancestry. DRAIN has no new report or primary; its inherited DATA ancestors retain their evidence. The same predicate applies in own-session STATUS/NEWVIEW history validation, receipt-driven commitment and Completion. A receipt or QC is not an exemption for an unchecked current-session first-DATA ancestor.

**Late and historical processing.** A complete earlier-term proposal in the current generation retains the original Vote eligibility even after local term advancement. Reports are checked against its historical context and parent. Old-generation proposals remain archival without fresh votes/timers; future-generation proposals remain buffered until entry; authenticated closure retains its original effect. The mandatory evidence-first path continues inspecting original signed material even if the REPORT sidecar is invalid, incomplete or missing. The new rule must not weaken the original definition/detection of admissible DATA/DRAIN or NEWVIEW equivocation by hiding original evidence behind a malformed new wrapper.

Sidecar signer subsets/encodings are validation-witness variants. Proposal identity remains `(beta,r,g,t,j,H(B))`; a new sidecar for the same original proposal does not manufacture equivocation, start another timer or defeat deduplication. Changed primary bytes change the ordinary DATA hash, so the existing one-block-per-position rule covers them.

## 5. No extra acquisition round and no spurious progress BLAME

Write `e=min_v e_v(V)` over correct members and use the installed `Delta`. The statements retain the original qualifications: current, unfrozen, uncompleted/unclosed interval; complete prepared entry where required; and the abstract complete-handler processing scope of Section 2. They do not assume simultaneous authority delivery.

### Ordinary term `t>0`

The preceding complete terminal QC has a correct signer. Its forwarded complete proposal makes all correct members vote and form that QC within `2 Delta` of first correct QC receipt. This part of Part I's handoff proof does not depend on the new leader's next proposal (`Part I:630–657`). Thus all correct members have entered the successor term and have its exact parent by `e+2 Delta`. They send their immutable local reports in those handlers. All correct reports reach a correct successor by `e+3 Delta`, and correct weight alone exceeds `F`.

The leader also has the original parent QC by then. It proposes immediately when both inputs exist, so all correct members complete validation and vote for first DATA by `e+4 Delta`. No `AcquirePending`, post-entry wait or complete-pool response is involved.

### Initial/recovery term zero

For initial entry use the existing complete ReadyBundle/Enter contract (`main:2039–2050`). For recovery use the original prepared/cached-authority entry argument (`live:113–139`), not a new bound on arbitrary authority availability. Entry skew is at most `Delta`. A correct initializer finishes its original `2 Delta` wait by `e+3 Delta`; its complete valid NEWVIEW reaches all correct members by `e+4 Delta`.

Each receiver sends its original ANCHOR-VOTE immediately and its independent local REPORT in that same completed opening-handler event. Both correct-only certificate inputs reach the leader by `e+5 Delta`. First DATA reaches and is voted by every correct member by `e+6 Delta`. No report is required for DRAIN, whose old timing is unchanged.

### Remaining positions and the actual deadline

After the first position, a vote round and next proposal add at most `2 Delta` per position. For the `p`th fresh DATA position, `p>=1`, the resulting bounds are

`ordinary: e+(2p+2) Delta <= e_v+(2p+4) Delta`,

`term zero: e+(2p+4) Delta <= e_v+(2p+4) Delta`.

These are complete validation/Vote events at the replicas, not merely sends or votes arriving back at the leader. They meet the original `main:1211–1229` progress checks. At equality the existing message-before-timer order applies. Consequently no correct member supplies progress BLAME against a correct leader before the first correct freeze, just as in the original lemma. Incorrect/missing Byzantine reports cannot delay this path: every correct contribution is complete and eligible or EMPTY, and correct weight alone is sufficient.

The old sharper ordinary-handoff statement “first proposal by `q+Delta`, votes by `q+2Delta`” is replaced by the bounds above. It must not be copied unchanged into the new candidate. The deadline and the later global progress proof use the weaker bounds they actually need, which still hold.

## 6. Why the existing safety and DATA-progress arguments survive

This section records proof obligations discharged by the construction, rather than assuming that an added validity gate automatically preserves liveness.

**One chain or evidence.** The original signed DATA/NEWVIEW objects, block positions, parent rules and equivocation checks are unchanged. Additional deterministic witness validity restricts which proposals a correct member votes for. Correct forwarders include every required REPORT sidecar. Two admissible inconsistent histories still expose the original fork evidence; different report certificates on the same DATA do not create a fork.

**Protecting QC and locks.** Start with an actual correct Vote on an augmented-valid proposal at time `s`. Its complete forwarding contains the same context/parent/REPORT evidence that all other correct recipients can validate without a private-queue veto. Before any freeze or observable closure, every correct recipient can therefore cast the original matching DATA vote within `Delta`. The original evidence/closure-first proof then gives the protecting QC, timer protection and later entry-lock inheritance. REPORT has no rank and cannot update or override a lock. This is the precise reason that validator-local FIFO or report-choice vetoes are forbidden.

**Receipt/Completion.** An actual correct FINAL still comes only from the original timer-origin commitment. Own-session receipt processing requires `R+`, and first-complete-receipt relay transmits its regional sidecars. The original Completion cancellation and retirement drain proofs are unchanged once “complete regional bundle” in their regional handlers means `R+`. Public offers separately mean `R0`.

**Faulty-term bound.** The existing last progress check remains at most `u+(2K+6) Delta` from first correct term entry `u` in the prepared execution. If any correct member voted for the terminal proposal, its complete augmented forwarding produces the required correct votes/QC within another `2 Delta` unless Quit/closure intervenes. If none did, no terminal QC can have advanced a correct member, and the existing last checks yield a BLAME proof. No report task suppresses those checks. Therefore the unchanged conservative `(2K+12) Delta` bound for advancement, freeze or complete-result outcome still applies (`live:119–139`).

**Correct initializer window.** Its first proposal and local Vote still occur by `e+5 Delta`. Section 5 forbids correct term-zero progress BLAME. A later-term correct BLAME signer could enter that term only after the initializer's signed first DATA exists; its first complaint is at least another `6 Delta` after its own entry. Under the original no-revealed-equivocation suffix, the first proposal retains the protected timer window. All correct commits by `e+8 Delta` and a complete FINAL receipt by `e+9 Delta` remain available. REPORT sidecars were already received at Vote, so they create no second evidence-collection wait at receipt formation.

**Prepared replay and global DATA growth.** Keeping the unchanged term/initializer bounds preserves the existing `D_i=(Q+1)(2K+12) Delta_i` and `R_i` calculation in `live`. The required regional sidecars are retained/forwarded under the same fixed-session data duties; an old original public result is not treated as complete augmented own-session recovery input. Cross-session inherited anchors use the already established historical kernel rule and need no new producer-REPORT retrieval. Thus the old finite preparation dependency set and original public `R0` service are not expanded by an invented public archive lookup. With these explicit interfaces, the v3.7 public-response, accepted-DATA growth and repeated regional DATA arguments retain their stated model scope. This is a source-level preservation argument, not a machine-checked whole-protocol certification or a concrete throughput benchmark.

## 7. Regional retention and bad/late packets

The companion fragment also makes the minimal within-snapshot request relay explicit. On first full authenticated admissible request receipt, a correct node persists the pending request and dispatches it to every authenticated installed regional snapshot in which it is a member, deduplicated per request/snapshot. Learning a new such snapshot schedules individual relays of retained requests; it adds no whole-pool completion gate. Pending request storage and relay duties survive Closed/Terminated because this is data transport, not fresh BFT signing. From a correct member's actual complete first receipt and immediate dispatch, all correct members of that installed snapshot receive the request within the existing `Delta`. This does not bound backlog dispatch, discovery or transport between disjoint rosters, and does not establish when a new roster first has a correct holder.

Correct reporters retain their signed report/body; correct leaders retain the certificate and selected primary in the full proposal bundle. Correct voters retain and forward all regional sidecars required by their proposal and ancestry. STATUS/NEWVIEW, QC histories, complete receipts and retirement ownership transfers include the applicable `WR`. A bare hash or private retrieval promise is not a complete regional dependency. A correct sender supplies the bytes or an already established reference resolvable within the original intra-region complete-message bound.

The retirement owner takes `WR` with the existing required signed evidence and receives the late-message route before releasing the old owner. Fresh INPUT_REPORT signing joins the existing fresh-action gate; evidence forwarding and serving do not. No report response resurrects a terminated engine or changes an old timer. ## 9. Monotone finite-predecessor progress on accepted ancestry

The following lemma is independent of whether successive sessions have the same roster. It isolates the node-level awareness condition that a separate changing-membership construction must establish.

Fix a logical request `x` that fits alone and remains admissible immediately after every relevant eventual accepted parent until its first inclusion. For a genuine context `RC` with parent `P`, call its actual certificate **x-covering** if it contains a correct member whose retained eligible set contained `x` when that member issued its immutable report. It is sufficient, but stronger than necessary, that all correct members of the context's actual roster held eligible `x` before issuing their reports. Since every `>F` certificate contains a correct signer, that stronger node-level property makes every possible valid certificate x-covering.

**One-step lemma.** If a term-first DATA `B` with an x-covering genuine witness becomes accepted, and `x` is not already accepted through its parent ancestry, its primary is an actual request `z` with `key(z)<=key(x)` and `id(z)` absent from the previously accepted prefix.

**Proof.** The aware correct signer chooses a local minimum `y<=x`. The certificate minimum satisfies `z<=y<=x`. Full validation checks that `z` is a real authenticated, admissible request executed first and absent from `Anc(P)`. Acceptance extends `G` along that exact ancestry. Immediately before appending `B`, its parent DATA history is the accepted prefix through `P`, including any ancestors accepted in the same EXPORT. Hence `id(z)` was not already there. If `P` contains `x`, accepting that ancestry already satisfies the objective and the excluded case applies. The argument does not assume the proposer is correct. ∎

Let

`S_x = {canonical authenticated request representations u : key(u)<=key(x)}`

and define the mathematical potential

`Phi_x(G) = |{id(u): u in S_x and id(u) does not occur in G}|`.

`S_x` is finite: each representation has length at most `len(enc(x))`, and there are finitely many byte strings of bounded length. Only actual well-formed representations/identities need count; considering all such strings is an overestimate. The bound can be astronomically large and provides no useful latency guarantee.

Because `G` only extends, `Phi_x(G)` never increases. Every accepted x-covering term-first DATA while `x` is absent strictly decreases it by the one-step lemma. Other accepted requests can decrease it further; nothing can increase it. Consequently there cannot be infinitely many such accepted first-DATA events while `x` stays absent. Quantitatively, after at most the initial finite number of distinct predecessor identities plus one relevant successful selection, either `x` has appeared or the alleged sequence is impossible.

This potential deliberately ignores regional commitment, a locally preferred branch, a fresh session queue, and the count of unsuccessful proposals. A predecessor can be proposed or regionally committed repeatedly on discarded forks without spending or replenishing `Phi_x`. Once it is spent by acceptance, every later accepted parent ancestry contains it, so the explicit ancestry exclusion prevents reuse as another accepted primary. Force retains `G`; recovery and speculative parent replacement therefore cannot reset the argument.

**From accepted DATA to term-first events.** Each actual DATA-producing term has at most `K` DATA positions. Every genuine validated DATA proposal has a same-term first-DATA ancestor at most `K-1` DATA steps earlier; recovery just starts a new term with its own first DATA. A contiguous accepted history cannot accept the later DATA while skipping that ancestor. Even if one exact block admits several historical proposal wrappers, choose the genuine witnesses supplied by actual validation/FINAL origin: distance at most `K-1` is enough. Finitely many first-DATA ancestor block identities can cover only finitely many accepted DATA heights. Hence unbounded accepted DATA entails infinitely many distinct accepted term-first block events. DRAIN contributes no DATA height and no fresh request opportunity.

For a particular region's repeated accepted contributions, apply the same argument to that region's genuine current-session terms: a same-term first DATA is produced by that region and is accepted with its descendants. Finite per-term length, not fixed membership across sessions or bounded session count, is the counting fact.

**Conditional inclusion theorem.** In an arbitrary sequence of valid session rosters, suppose the preserved DATA-progress result supplies infinitely many accepted term-first events whose genuine certificates are x-covering. Then `x` enters `G`. The proof is the finite-potential contradiction above. No assumption of stable membership appears in that implication; proving its awareness premise is a separate necessary task.

## 10. Immutable first reports, new arrivals, and the precise remaining gap

Immutable first reports suffice asymptotically **once the relevant awareness events precede all but finitely many of the counted accepted report contexts**, or otherwise yield infinitely many x-covering accepted contexts. They do not need to change every time another request arrives.

At any one exact view/parent, a member can report EMPTY, receive `x` later, and retain the EMPTY report. A Byzantine leader can use that old certificate to omit `x` from that term. This is permitted and does not invalidate the algorithm. That term has at most `K` DATA positions. It cannot produce an unbounded accepted DATA suffix under the same report context. Later ordinary terms, recovery generations and Force sessions use changed contexts and take new local snapshots. An honest leader with an all-EMPTY certificate can also include the newly arrived `x` by ordinary FIFO filling.

For a finite dissemination event in the ordinary locally finite execution-event semantics, there are only finitely many previously issued report contexts. Delayed publication may accept some of them much later, but each contributes only finitely many DATA positions. This eliminates a finite stock of frozen pre-awareness reports; it does not assume a positive lower bound on individual message delays or a shared real-time cutoff known by nodes.

The changing-membership limitation is exact. A node-level statement “every roster eventually receives `x`” is insufficient if infinitely many disjoint rosters issue their immutable EMPTY reports and contribute their accepted DATA **before** their respective delivery events. Each late delivery can be finite while every accepted witness stays unaware.
