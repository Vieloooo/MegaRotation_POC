# v3.10 → v3.11：收到 OC 后必须转发

v3.10 已把请求接力、Ready 前的精确 anchor 选择和完整请求证明接入正文。新的[活性审查](../v3_10/fresh_progress.md)发现一处实际遗漏，故未将它认定为完成版。

设正确成员 H0、H1 和恶意成员 B 各一份权重，F=1。H0 已广播自己的 offer。B 用 H0 的 offer 加上自己的较大 key，拼出一份有效 OC，只把完整证书发给 H1。OC 的最小 key 属于 H0，所以验证它不需要 B 的非最小请求 body。H1 可以采用 OC 并取消自己的重复计算；但旧文只明确了“自己组出 OC 时广播”，没有规定“收到别人组出的 OC 时也广播”。若 session 已关闭，Ready 不会触发。H0 因而可能始终得不到完整 OC。

v3.11 明确规定：

1. 第一次验证得到某个 K 的有效 OC，无论自己组出还是别人发来，都先持久保存证书并登记向所有目标成员发送的任务。
2. 登记后才允许取消重复计算或通知 Ready。实际发送继续完成；关闭 session 或退出 worker 不取消它。
3. 每个 K 只触发一次首次持有广播；重复输入只继续未完成的发送。该去重不妨碍采用同 K 的另一份有效 OC。
4. 转发已经有效的 OC 只需其选中的请求 body，不等待非最小 key 的 body。

形成证明分两种情况：有人已取得 OC，就由这项持久职责传播；否则正确成员继续自己的有限计算并发送 offer，足够正确权重最终组成 OC，再走同一个传播步骤。

另外修正了 OC 长度公式中 indicator 的 LaTeX 反斜杠，并依据用户对原输入条件的确认补齐 ingress 的操作含义：送达 region 表示每个成员最终收到；证明只用一个正确 owner 的实际完整收件事件。该说明没有改动 v3.1 Model 原文或增加客户端时限。

本版仍需新的独立审查。修补不会改变 Force cutoff、四字段 view、regular DATA/DRAIN 或原公共 R0。
