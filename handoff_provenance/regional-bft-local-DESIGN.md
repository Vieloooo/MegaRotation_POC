# Regional BFT simulation and protocol integration

2026-11-07 · Implementation design · Commonware 2026.10.0 (release v2026.10.0, `92a2f68`)

This project runs equal-weight Regional BFT replicas on a laptop with a simulated network. The deployment experiment will run approximately 15 replicas on AWS. The first executable milestone exercises the released Commonware Simplex engine. Kudzu and Minimmit are separate backend designs in this document. The Commonware release exports Simplex as its consensus engine. `aggregation` is a quorum-certificate utility. [Release](https://github.com/commonwarexyz/monorepo/releases/tag/v2026.10.0) · [Consensus exports](https://docs.rs/commonware-consensus/2026.10.0/commonware_consensus/)

## 1. Model and experiment boundary

A run fixes an ordered committee $V=(0,\ldots,n-1)$ with one vote per identity, its public keys, one anchor, an application input stream, a leader schedule, a protocol version, and that version's quorum and timing parameters. $f$ is the configured Byzantine bound, $b$ the actual Byzantine count, and $o$ the number of additional unavailable replicas in the scenario. The configured committee survives crashes and restarts. In a liveness experiment with persistent faults, count $b+o$ against the protocol's guaranteed participation budget. A fault schedule fixes the corrupt identities and directed link behavior in virtual time. A restart reopens the same replica's durable journal.

The intended primary experiment uses $n=15$ and per-view scheduled leaders. Run the same no-fault, one-fault, and two-fault scenarios against all backends, and identify the guarantees under each configured profile. Test three and four faults separately for the Simplex and Kudzu configurations. A fault count outside a profile's bound is a stress experiment. For progress assertions, declare the post-heal delay, available peers and data, and the ready interval. Healing a partition that dropped messages requires an explicit retransmission or repair scenario. In particular, the synchronous interval in Kudzu §3.1 constrains previously sent messages as well as fresh ones. Treat lossy runs with unverified repair behavior as empirical. [Kudzu v2 §3](https://arxiv.org/html/2505.08771v2#S3)

A physical block has a canonical encoding containing its parent hash, height, and body, with benchmark applications using a deterministic validity predicate over the full block and its parent. Payload validation covers reconstructed bytes as well as bodies received intact. View, application height, and session identity are separate coordinates. A `Context` fixes the committee, anchor, protocol and verifier versions, and all parameters that affect admissibility. Its identity is a domain-separated digest of its canonical encoding. A protocol message's signed subject binds that context, its message kind, the view, and the exact proposal or timeout subject. Where the protocol votes on a coding root, the signed proposal binds the root and the data needed to recover and identify the block. A namespace can bind the context when a native Commonware message supplies the remaining coordinates. A storage partition or network channel name alone does not provide signature binding.

The MegaRotation `Session Program` (`formalization_v9/02_session_program_zh_v0_1.md` §§3–4, parent project revision `484d55572e47a9729eb1b140728077b51079e0af`) is the intended integration contract. The executable smoke harness uses the upstream test application and a shared in-memory relay for synthetic payloads. Its votes, certificates and resolver messages travel over the simulated links. It exercises the real Simplex engine and BLS12-381 multisignatures. The shared relay omits block-body network costs and is a wiring fixture for the full delivery profile. The weighted committee, production `Build/Accept/NotBefore` rules, lifecycle and stop enforcement, and global admission through GFR are separate integration obligations.

## 2. Commonware interface

The following interfaces are from the pinned Commonware source. The project should use their concrete Rust types at the adapter boundary.

| --- | --- | --- |

| Application | `Automaton::propose`, `Automaton::verify`, `CertifiableAutomaton::{certify, prepare}`, `Application` | The low-level proposal and verification hooks asynchronously return a one-shot receiver. | Blocks and codecs | `Block`, `BoundedBlock`, `CertifiableBlock`, `commonware_codec` | Bound sizes at decode, use canonical encoding and a fixed digest algorithm, and bind any embedded context through the digest. ### 2.1 Project adapter contract

These operation names describe the proposed project boundary. Each backend owns its vote pool, state transition rules, local timers, and proof type.

| Operation or event | Inputs and behavior |
| --- | --- |
| `Start(context, replica, services)` | Validate the configuration and key index. Open the replica's journal, restore it if present, and start the state machine on the supplied clock and network. Reject mismatched persisted context or unsupported parameters. |
| `Build(parent, round)` | Construct a canonical block on the consensus-selected parent from the fixed workload. Return an available block, a pending request for missing inputs, or a rejection. |
| `Validate(parent, block, round)` | Check the block, its binding to the proposal, and the application predicate. A missing parent, body or application input leaves the request pending. For the synthetic application, terminal validity is the same at all honest nodes given the same inputs. |
| `CheckFinal(context, block, proof)` | Decode the protocol-tagged proof using the pinned verifier. Check the context, subject and threshold, plus any proof-specific evidence required by §3. This predicate uses only the public inputs. A direct proof authenticates its target. Finality for an ancestor requires a verified hash-linked path from the target to that ancestor. |
| `ProofObserved(replica, round, block_id, kind)` | A decision certificate has passed cryptographic verification for this context. Timestamp the observation even when the body is missing. |
| `Delivered(replica, tip, prefix)` | The replica can supply a contiguous, validated prefix from its anchor, covered by finality evidence. Emit delivery once per newly finalized block identity in the experiment output, including blocks finalized indirectly by a descendant. Retain the certificate and ancestry needed to reproduce the check. |

For the eventual Session Program adapter, `Build` must honor `NotBefore`, and proposal validation must preserve the first receive time across retries. Commonware treats a resolved or dropped verification or certification response as terminal for the request. Represent missing inputs by a pending response and cancel work when the request is abandoned. The production adapter needs an explicit distinction between context-wide payload validity and a node-local receive-time admission guard. The latter may differ across replicas and cannot simply be substituted for Commonware's deterministic validity predicate. Close/stop must gate creation of new signatures, including after restart. A signature made before stop can still be assembled later. Check `BFT-2` before a block is first used as a parent or decided, including early voting, first-shard voting, and any vote triggered by a certificate. Integration with the production time and validity guards requires its own conformance tests and safety argument.

## 3. Paper rules and backend mappings

| Backend at $n=15$ | Configured bound | Continuation and skip | Direct decision certificate |
| --- | --- | --- | --- |
| Commonware Simplex | $f=\lfloor(n-1)/3\rfloor=4$ | 11 notarize or nullify votes. Successful continuation from notarization also uses certification. | 11 finalize votes |
| Kudzu v2 | $f=4,p=1$, with $n=3f+2p+1$ | 10 notarization or timeout votes. A successful continuation also needs a complete block. | 14 First votes on a real block, or 10 Final votes, with the target complete at the deciding replica |
| Minimmit v5 | $f=2$, with $n\ge 5f+1$ | 5 votes for an M-notarisation or 5 nullify votes | 13 votes for an L-notarisation |

### 3.1 Simplex

Chan and Pass define a leader-proposal, notarization and decision protocol with signed evidence for skipped views. The explanatory protocol's at-least-two-thirds threshold and Commonware's `N3f1::quorum(n) = n - floor((n-1)/3)` are different conventions at $n=15$. Use Commonware's 11 in the executable baseline. [Simplex paper](https://eprint.iacr.org/2023/463) · [Protocol explanation](https://simplex.blog/protocol/) · [Commonware quorum code](https://github.com/commonwarexyz/monorepo/blob/v2026.10.0/utils/src/faults.rs)

Map to the released engine and use its native proposer, notarize, nullify, and finalize subjects. A valid child extends a finalized or notarized-and-certified parent, with the intervening views covered by nullification evidence as required by the configured term policy. After notarization, the application certifies the payload before normal advancement and the finalize vote, subject to the voter's nullification and equivocation guards. A verified finalization authenticates that block and determines its ancestors. Notarization, certification, and nullification are distinct observations. Keep the upstream timeout, replay and resolver behavior and record each setting. [Pinned engine protocol and deviations](https://github.com/commonwarexyz/monorepo/blob/v2026.10.0/consensus/src/simplex/mod.rs)

### 3.2 Kudzu

Use Shoup, Sliwinski and Vonlanthen, v2 §§3.3 and 4, Protocols 1–2. The backend owns the certificate pool, complete block tree, current slot, current parent, first-vote map, set of notarized subjects and second-look state. The proposal binds slot, parent hash and an information dispersal commitment. The leader sends one indexed shard with its proof to each replica. An initial voter checks leader authentication, its indexed shard proof, complete parent and certificates for the skipped slots. It sends at most one FirstVote per slot with a First signature and an embedded NotarVote, including the shard and proof for a real block. It may instead first-vote for the timeout block at the paper's deadline. [Kudzu v2 §4](https://arxiv.org/html/2505.08771v2#S4)

After first-voting, the replica can take a second look at a block with at least $f+p+1=6$ distinct first voters and a complete parent. It reconstructs and validates the payload before sending an additional notarization vote, or sends a timeout notarization vote if reconstruction or validation fails. The paper also permits timeout notarization when the number of recorded first voters minus the largest count for any real block reaches 6. Deduplicate by the relevant vote kind, slot and signer according to the paper. First votes, additional notarizations, and timeouts use their distinct admissibility rules.

A block enters the complete tree only with a NotarCert, a complete parent, and an application-valid decoding from at least 6 distinct certified fragments. In the active slot, a complete real block can become the next parent. A replica sends FinalVote on that branch only if all subjects it previously notarized for that slot are the chosen block, including the case of no earlier notarization. On a timeout certificate the replica exits the current slot with its selected parent unchanged. Finalization is a complete block plus a FirstCert or FinalCert. Its ancestors finalize implicitly. [Kudzu v2 §§4.2–4.7](https://arxiv.org/html/2505.08771v2#S4)

Map certificate assembly and cryptographic verification to Commonware, with separate First, Notar and Final subjects and quorum policies. Map information dispersal to authenticated Reed–Solomon with `minimum_shards=6` and `extra_shards=9`. Check index ownership, the fixed coding configuration and data bounds, and binding of the decoded block to the signed commitment. Preserve the fragment-carrying notarizations and complete-tree rules. A verifier may log the cryptographic FirstCert or FinalCert before it has enough information to check completeness. The backend's decision and delivery require the protocol's completion conditions. The public decision witness includes the target NotarCert, the complete decoded block bound to the commitment, and authenticated complete-parent evidence back to the fixed anchor. Retain or recover those objects before exporting the decision. The receiver can check the commitment by re-encoding the body.

### 3.3 Minimmit

Use Chou, Lewis-Pye and O'Grady, v5 §4 Algorithm 1 and §5. The backend owns the current view, vote and nullify flags, received evidence and parent selection. The base proposal rule uses the highest prior M-notarised parent with the paper's tie-break, and the ordinary voting rule requires exactly one known leader-signed block for the current view, an M-notarisation of its matching parent, and a nullification for every intervening view. Record one block vote per honest replica per view. In addition to the normal proposal path, Algorithm 1 lines 19–21 require a previously unvoted and un-nullified replica to vote on a current-view M-notarisation before advancing. Preserve this path when adapting digest votes and missing bodies. [Minimmit v5 §§4–5](https://arxiv.org/html/2508.10862v5#S4)

An unvoted replica may nullify at $2\Delta$. A replica that already voted may nullify when it observes $2f+1$ distinct same-view senders of nullify messages or votes for a block different from its own. Maintain the paper's view-scoped evidence and forwarding of newly acquired M-notarisations and nullifications. A replica advances on an M-notarisation or nullification and checks L-notarisations even when they arrive for an earlier view. The L-notarisation decides the block and its ancestors. The M-notarisation provides progression evidence. For a given view, the paper rules out both an L-notarisation and a nullification, and rules out an M-notarisation for a conflicting block once an L-notarisation exists.

Map block votes and nullify votes to separate signed subjects and encode the M/L certificate kind with the verifier's exact threshold policy. A vote can support either certificate class. Track signer-unique individual attestations for the after-vote nullification rule. Map digest voting, body repair and optional coded delivery using v5 §§6.2–6.3. In the paper's coded profile, $d=f+1=3$ and votes carry their checked fragments. An M quorum contains at least $d$ correct participants under its fault bound. Increasing $d$ to match Kudzu's shard size changes the availability argument and needs separate analysis. [Minimmit v5 §6](https://arxiv.org/html/2508.10862v5#S6)

## 4. Shared optimization profiles

Enable Commonware's applicable shared optimizations in the controlled profile, using the same implementation and settings on all backends where the paper's guards permit them. An optimization that changes vote eligibility, quorum, parent selection, leader schedule, recovery, evidence attribution or data readiness is part of the protocol profile. An alternative implementation of the same primitive is a separate configuration. Record those differences alongside the results so a whole-stack speedup is not attributed to the vote algorithm alone.

| Optimization | Controlled policy and compatibility check |
| --- | --- |
| Aggregated signatures | Use Commonware attributable BLS12-381 multisignatures as the shared optimized target. Pin the key format and registered ordered signer set, require proof of possession for multi-signature keys, and verify both the aggregate and the signer bitmap against the expected per-kind threshold. The Simplex multisig wrapper is bound to `N3f1`. Custom subjects and threshold policies for Kudzu and Minimmit need their own adapters and tests, with the threshold determined independently of the input certificate. |
| Batched validation and parallelism | Reuse the release's batch signature verification, certificate assembly, hash batching, parallel strategy and SIMD path when applicable. The same concurrency and batch policies apply for matched runs. Optimistic assembly may prove a certificate without authenticating every input vote individually. Verify individual votes before using them in conflict evidence or per-signer triggers. |
| Threshold BLS, Ed25519 and VRF | Treat these as explicit alternative profiles. Threshold certificates require key setup for each distinct quorum and separate verification domains, including Kudzu's 10 and 14 and Minimmit's 5 and 13 at $n=15$. Evidence attribution and leader selection must be rechecked. Ed25519 supports batch verification with a different wire cost. Dynamic leader selection and a predetermined rotation use separate experiments. |
| Digest votes, coded delivery and repair | Use the shared codec, hash, Reed–Solomon implementation with authenticated shards, bounded buffers, and a common repair policy where compatible. The release removed ZODA. Fix payload bytes, topology, pacing, network budgets and observation endpoints. Record the shard counts, bytes and eligibility rule for each protocol. Report protocol-native coded runs as consensus plus its required data path. A matched full-body or matched coding profile is valid only when each backend preserves its stated rules with that delivery configuration. |
| Journaling and message handling | Reuse Commonware storage, durable batches, codec bounds, buffering and backpressure. Keep the same durability and bandwidth conditions. Record implementation-specific journal batching, retries, caching and pruning. Any change that drops needed certificates or lowers durability has a separate review and experiment. |
| Simplex-specific scheduling | Per-view rotation, with stable terms, optimistic lookahead, early skip and pipelined handoff disabled or inapplicable, is the controlled baseline. Test these mechanisms separately in a Simplex optimized profile. Moving application checks to certification can admit notarize votes before full validation and has separate `BFT-2` obligations. |

## 5. Implementation verification and benchmark acceptance

Keep a conformance record for each backend with the paper section or upstream function, implementation handler, local state and sign-once guard, expected event, and one test or review reference. The baseline smoke run exercises wiring and finalization. The checks below are gates for adding a backend to the comparison.

| Check | Acceptance evidence |
| --- | --- |
| Certificate boundary | Each kind rejects one fewer than its threshold, duplicate signers, forged or wrong-kind signatures, altered block/parent/coding commitments, wrong view/context and malformed encodings. Exactly the threshold of valid distinct signers verifies. An M-notarisation, NotarCert, or skip proof never passes the final-proof entry point. |
| Agreement and delivery | Independent trace checker verifies final evidence and ancestry from encoded artifacts. Compare all independently verified decision witnesses and compare delivered prefixes between honest observers within one context. Retain verified but undelivered proofs as pending until their ancestry can be checked, and report unresolved proofs at cutoff. Compare every delivered block with the input validity predicate. A progress scenario must produce at least one verified decision and delivery. Feed an intentionally conflicting and an invalid-body trace to ensure the checker rejects both. |
| Correctness under failure | Script leader equivocation, withholding, partition and heal, out-of-order evidence, duplicate frames, restart before and after vote persistence, and corruption or withholding of shards. Test a malicious encoder whose individually authenticated shards fail the decode and re-encode commitment check. Preserve the actual signed messages, simulated clock, and seed. Run a post-heal progress assertion only after the conditions in §1 hold. |
| Protocol-specific traces | Simplex rejects a skipped-parent extension lacking nullification evidence and never delivers on notarization alone. Kudzu exercises the fast path with one silent replica, a slow decision with two silent replicas and a live honest leader, second-look reconstruction, and refusal to deliver when a FirstCert arrives without a complete block. Minimmit exercises a 5-vote advance without delivery, a 13-vote decision, an M-triggered vote, after-vote nullification based on distinct senders, and the ordinary vote guard when two signed leader proposals arrive before voting. |
| Boundary integration | Test close/stop during pending validation, replay of pre-stop signatures, persistence after restart, same view under a different context, and absence of application-invalid parents. These are requirements for the Session Program adapter. |
| Independent review | One reviewer reads the pinned paper and code without relying on the implementer's summary, then checks the negative traces and wire evidence. A protocol owner reviews sign-once, quorum, data-availability, and recovery changes. Any finite exploration records its committee size, state abstraction and search bound. |

Use a short local suite on every change and broader seeded runs before comparing performance. Save the release and backend revision, full profile, input and link schedule, independent workload/network seeds, engine seed, event traces, and command for each run. Replay the same build/profile/seed and check the canonical event trace or trace digest. Sharing a seed alone cannot align different engines' message streams. Compare them under paired external input and link schedules.

Report view duration, time from submission and proposal to a verified decision proof, time to deliver the corresponding contiguous prefix, useful throughput, pending or failed requests at cutoff, per-channel bytes and repair traffic. A Mac simulation measures these latencies in virtual time. Its wall time measures simulator cost. On AWS, run the same backend and workload adapters with real authenticated transport and storage. Use observer-local monotonic durations for end-to-end latency and synchronized clocks only where the experiment measures one-way timing. Publish per-profile fault assumptions and shared versus native optimization settings with each result. A passing finite test suite supplies implementation evidence for the exercised schedules.
